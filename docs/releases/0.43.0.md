# phax 0.43.0

Changes since 0.42.0: [v0.42.0...v0.43.0](https://github.com/lbdremy/phax/compare/v0.42.0...v0.43.0).

## Highlights

- **Gate step times in the gate attribution** — A gate time is a recorded fact read from the record, never a guess, a re-run, or a reason to change a verdict.
- **Launcher and release-pipeline fixes: verified first run, forwarded signals, tag-only redeploy, locked Deno build** — Only verified, pinned code reaches a user's machine or the release, and the launcher is a transparent doorway to the binary it verified.
- **Security High fixes: skeleton records, worktree git, .phax-context, review skill** — Nothing the agent under review can write decides what phax executes, where phax writes, what phax publishes, or how the agent's work is reviewed.
- **The plan names its gate profile** — The profile that gates a run is the one the operator approved in its plan, never the one phax.json happens to list first.

## Upgrading

- **`gate-attribution.json` and `checks-attempt-NN.attribution.json` move to a new shape**, stamped 0.43.0, with a required `time` on the attempt, on every step and on a non-null `protectedPaths`: `measured` with `startedAt` and `durationMs`, or `not-run` for a skipped acceptance step.
- **`phax records explain` shows these times** under its `gates` line, and `--json` adds `gateAttempts`.
- **Older attributions still read, with their times `unknown`, and are never rewritten.**
- **An `@lbdremy/phax-schemas` before 0.43.0 cannot read the new attributions**, so upgrade the package. Its `toLatestGateAttribution` gives 0.26.0 to 0.33.0 attributions `unknown` times. Older ones (pre-schema, 0.17.0 to 0.21.0) come back under their own types with no `time` key, since their steps can be `pending`; phax itself reads them with `unknown` times.
- **Phase records carry the required `gateProfile`**, the id of the gate profile that gated the run, and `phase-record-manifest` is stamped 0.43.0. `phax records explain` prints it on a `profile` line just before the `gates` line, and `--json` adds `gateProfile`.
- **Earlier records read as `null`**, shown as `(not recorded)` by `phax records explain`, and are never rewritten. `toLatestPhaseRecordManifest` lifts them the same way.
- **An `@lbdremy/phax-schemas` before 0.43.0 cannot read the new records**, so upgrade the package.
- **A plan's JSON sidecar carries the required `run.gateProfile`**, the id of the one gate profile in phax.json that verifies the plan's whole run, and `plan-document` is stamped 0.43.0. The rendered plan.md declares it in a `## Gate profile` section, just before `## Required commands`. A document without it is refused, naming `run.gateProfile`.
- **An `@lbdremy/phax-schemas` before 0.43.0 cannot read the new plan documents**, so upgrade the package. Its `toLatestPlanDocument` lifts a plan document stamped 0.38.0 or earlier under a type of its own, `LiftedPlanDocument`, whose run declares no gate profile: it never invents one.
- **A plan sidecar stamped 0.38.0 or earlier declares no gate profile.** It still reads, but `phax artifact approve` and `phax artifact reopen` refuse it until it is migrated.
- **Every plan.md declares exactly one gate profile under `## Gate profile`**, its id written as a code span or a bare word. phax reads it itself and never asks the extraction model. `phax plans lint` reports a plan with no declaration, or more than one, as a `structure` error, and extraction refuses it before any model call, naming `phax plans lint`. `phax plans overview`, `phax plans estimate` and `phax plans overlap` only show a plan: they do not read its gate profile, so a plan written before the declaration, archived ones included, still shows.
- **`phax-plan.json` carries the required `run.gateProfile`**, and `phax-plan` is stamped 0.43.0. A run started by 0.42.0 or earlier recorded none: it is still listed and shown, but `phax resume` refuses it. Finish it with the release that started it, or archive it with `phax archive <run> --force` and run its plan again. An `@lbdremy/phax-schemas` before 0.43.0 cannot read the new file; its `toLatestPhaxPlan` lifts one stamped 0.38.0 or earlier under a type of its own, `LiftedPhaxPlan`, whose run names no gate profile.
- **A plan whose extraction fell back to the model is extracted once more**, since an extraction cached by an earlier release is a miss.
- **`phax run`, `phax run --dry-run` and `phax plans lint` use the gate profile the plan declares**, wherever phax.json lists it, never the first one. Revise each live plan to declare one and approve it again. `phax run` refuses a declared profile phax.json does not define with exit 2, before any worktree, run branch or run folder exists. See [Gate profiles](https://github.com/lbdremy/phax/blob/v0.43.0/docs/gate-profiles.md).
- **`phax plans lint` has a new `gate-profile` check**, an error naming the declared profile and every defined one when phax.json does not define it. The `commands` check then compares required commands with the declared profile's steps alone. Every lint report's check column is one space wider.
- **`plan-lint` is stamped 0.43.0**, and an `@lbdremy/phax-schemas` before 0.43.0 refuses new lint documents, so upgrade the package. It reads a 0.34.0 lint document as its own shape and `toLatestPlanLint` lifts it unchanged.

Run `phax artifact migrate-documents --gate-profile <id>` once per live plan sidecar stamped 0.38.0 or earlier, naming one of phax.json's gate profiles. It writes the id into the sidecar and renders `## Gate profile` into the body, so approve each Approved plan again afterwards. Without the flag such a plan is refused, naming the flag, and an id phax.json does not define is refused with exit 2.

### Launcher and release-pipeline fixes: verified first run, forwarded signals, tag-only redeploy, locked Deno build

> Only verified, pinned code reaches a user's machine or the release, and the launcher is a transparent doorway to the binary it verified.

- A first run that is interrupted, raced or fails leaves no binary behind, so the next run downloads and verifies again instead of running an unchecked file. `phax (npm launcher), first run`

  Now:

  ```text
  $ phax --version                 # first run of 0.44.0, killed during the download
  phax: downloading binary from https://github.com/lbdremy/phax/releases/download/v0.44.0/phax-darwin-arm64
  ^C
  $ ls -A ~/.phax/bin/0.44.0/
                                   # empty: the private download directory is gone
  $ phax --version                 # downloads and verifies again
  phax: downloading binary from https://github.com/lbdremy/phax/releases/download/v0.44.0/phax-darwin-arm64
  0.44.0
  ```

  <details>
  <summary>Before</summary>

  ```text
  $ phax --version                 # first run of 0.43.0, killed after the download
  ^C
  $ ls ~/.phax/bin/0.43.0/
  phax-darwin-arm64                # renamed in place, never verified
  $ phax --version                 # runs it, unchecked
  0.43.0
  ```

  </details>

- A first run that is redirected too far or off GitHub, or stalls, stops with a message naming the URL, host or timeout instead of looping, crashing or hanging. `phax (npm launcher), download errors`

  Now:

  ```text
  $ phax --version
  phax: download failed: more than 5 redirects from https://github.com/lbdremy/phax/releases/download/v0.44.0/phax-darwin-arm64
  $ echo $?
  1

  phax: download failed: refused redirect to http://release-assets.githubusercontent.com/…: not https
  phax: download failed: refused redirect to https://downloads.example.net/phax: host is not github.com or *.githubusercontent.com
  phax: download failed: no connection to github.com within 10 s
  phax: download failed: no data from release-assets.githubusercontent.com for 30 s
  ```

  <details>
  <summary>Before</summary>

  ```text
  $ phax --version     # a redirect loop: never returns
  $ phax --version     # relative Location
  TypeError [ERR_INVALID_URL]: Invalid URL
  $ phax --version     # stalled connection: never returns
  ```

  </details>

- Signalling the launcher stops the phax run it started, and the launcher's exit status is the binary's own code or signal. `phax (npm launcher), signals and exit status`

  Now:

  ```text
  $ phax run my-plan &
  $ kill -INT %1
  Run "my-plan" interrupted — state saved. Resume with: phax resume my-plan --yes
  $ wait %1; echo $?

  $ kill -TERM <binary pid>        # the binary dies of SIGTERM
  $ echo $?                        # the launcher died of SIGTERM too
  143
  ```

  <details>
  <summary>Before</summary>

  ```text
  $ phax run my-plan &             # through a manager that signals the launcher's pid only
  $ kill -INT %1
  $ echo $?
  130                              # the launcher died; phax-darwin-arm64 goes on with the phase

  $ kill -TERM <binary pid>
  $ echo $?                        # launcher's status
  1
  ```

  </details>
