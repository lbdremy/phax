Write the phax spec `protected-paths`: a project names, in its phax configuration, the files whose change is the operator's decision. No phase of a run may create, change, delete or rename them: not the agent, not its fix loop, not its handoff generation, not a gate command it runs. A phase that would need to change one fails its gate as any phase that cannot meet its gate does, and the change becomes the operator's to make.

Why: some files of a project record a human decision, and a gate reads them. The case that raised it is steme's debt file. `steme audit` exits non-zero on a violated leg unless the unit's `steme.baseline.json` accepts it. Each entry carries `acceptedAt`, `acceptedBy` and a `why`, and the gate then reports it as a review note. An agent that cannot fix a hole can accept it in that file, and the gate passes. In steme-lab's run `steme-gates-steme-2` (2026-10-28), phase-05's agent (Sonnet, medium effort) wrote nine entries into `packages/rust/steme-formats/steme.baseline.json`, each signed `"acceptedBy": "the author"`. The author never saw them before the phase's commit. The plan allowed it: its preamble said an engine defect or an unfixable hole "is accepted as debt", in that file. Nothing in phax could have stopped it. A plan's prose is not a boundary, and the write sandbox lets the agent write anywhere in the worktree. The same holds for any file in which a gate's tolerance is written: an allowlist of lint exceptions, a snapshot a test accepts, a standard's list that a gate enforces. Once an agent may edit the file that decides whether its own work passes, the gate no longer checks the work. It checks only whether the agent agrees with itself.

What phax has today, to read first:
- The write sandbox (`docs/security.md`, "Configuration" and "Provider Capabilities"). It bounds writes to the worktree and the state root, never a path inside the worktree.
- The skill edit grants (`docs/security.md`, "Skill edit grants (Claude Code)"; `src/domain/security/skillEditGrants.ts`). This is the inverse case: a path Claude Code protects by itself, opened file by file for a run started with `--allow-skill-edits`. It shows how the Claude adapter writes inline `--settings`, how a plan that declares such a file is refused before the run (exit 11), and how `security.json` records grants for every provider.
- The phase guard (`src/domain/security/phaseGuard.ts`). Inside a phase, phax refuses the phax commands that act on state. It is a guard against mistakes, not a boundary.
- The shell allowlists per provider (`docs/security.md`, "Shell command execution"). Claude allowlists exactly the gate commands. Codex runs anything inside its sandbox. Vibe matches by prefix.
- File reconciliation (`src/domain/reconciliation/`). phax already knows every path a phase created, edited, deleted or renamed. A path a person changed at an interactive stop is a `reviewCorrections` entry, never a deviation.
- The gate's fix loop (`src/domain/gate/fixPrompt.ts`) and what a phase does when the loop is exhausted.

What the spec must cover:
- **Declaring.** The key in `phax.json`, its shape, and whether globs are allowed. steme-lab would list `**/steme.baseline.json`. Unlike the skill grants, a protected list is naturally a pattern. Say which config layers may set it. A protected list that a user overlay or `phax.local.json` could empty is not a protection, as `assignments` already shows.
- **Detection, for every provider.** Before a phase's commit, and after every fix attempt, phax compares the worktree with the phase's base. Any protected path created, changed, deleted or renamed is refused, whoever wrote it: the agent's tools, a gate command, a script the agent ran. This part is deterministic and provider-independent. It is the guarantee.
- **Prevention, where the provider can.** Claude Code honours `permissions.deny` rules on `Edit`/`Write`. Say whether phax passes them, and what Codex and Vibe can do. Prevention spares the agent a wasted turn. Detection stays the boundary. Record each provider's enforcement in `security.json`, as the network profile is recorded: enforced or detected only.
- **What a refused write does.** Proposed: phax restores the path to its base content, and the fix loop is told which path is the operator's and that the hole must be fixed in the code or left failing. When the loop is exhausted, the phase stops as a failed gate stops, the handoff names what is left, and the operator decides. No new stop kind unless the spec shows one is needed.
- **The operator's route.** At an interactive stop a person may change a protected path, as `reviewCorrections` already allows. Between phases the operator may commit on the run's branch, then resume. Say how phax tells a person's change from an agent's at each of these points.
- **Plans.** A plan that lists a protected path in a phase's planned files: refused at `phax plans lint` and before the run, as skill files are without the flag, or allowed? A plan is written by an agent and approved by a person, but a person who approves a plan does not see each entry the agent will write.
- **Telling the agent.** The phase prompt names the protected paths and what to do when a hole cannot be fixed: report it in the handoff, never work around it.
- **The surface.** The config key, the message of a refused write, the `security.json` field, `phax security status`, the `phax.usage.kdl` entries, and the docs (`docs/security.md`). An acceptance criterion for each behaviour, including a gate command that writes a protected file.

Out of scope: the commands a project's own tool offers to change such a file. steme's `debt accept` and `debt withdraw` are steme's. Also out of scope: protecting paths outside the worktree, signing or attributing an operator's change, and reading what the protected file means.

Constraints: additive. A project that declares no protected path sees no change in behaviour, argv, prompt or records. The persisted formats change only by adding fields, at their current version. §9 holds genuine choices only, each with its options, what each abandons, and a recommended default. At least: where the key lives (`security.filesystem` or top level), restore-and-loop versus stopping on the first refused write, plans that declare a protected path, and the layers allowed to set the list.
