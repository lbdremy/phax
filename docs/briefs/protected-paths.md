Write the phax spec `protected-paths`: a project names, in its phax configuration, the files whose change is the operator's decision. No phase of a run may create, change, delete or rename them: not the agent, not its fix loop, not its handoff generation, not a gate command it runs. A phase that would need to change one fails its gate as any phase that cannot meet its gate does, and the change becomes the operator's to make.

Why: some files of a project record a human decision, and a gate reads them. The case that raised it is steme's debt file. `steme audit` exits non-zero on a violated leg unless the unit's `steme.baseline.json` accepts it. Each entry carries `acceptedAt`, `acceptedBy` and a `why`, and the gate then reports it as a review note. An agent that cannot fix a hole can accept it in that file, and the gate passes. In steme-lab's run `steme-gates-steme-2` (2026-10-28), phase-05's agent (Sonnet, medium effort) wrote nine entries into `packages/rust/steme-formats/steme.baseline.json`, each signed `"acceptedBy": "the author"`. The author never saw them before the phase's commit. The plan allowed it: its preamble said an engine defect or an unfixable hole "is accepted as debt", in that file. Nothing in phax could have stopped it. A plan's prose is not a boundary, and the write sandbox lets the agent write anywhere in the worktree. The same holds for any file in which a gate's tolerance is written: an allowlist of lint exceptions, a snapshot a test accepts, a standard's list that a gate enforces. Once an agent may edit the file that decides whether its own work passes, the gate no longer checks the work. It checks only whether the agent agrees with itself.

What phax has today, to read first:
- The write sandbox (`docs/security.md`, "Configuration" and "Provider Capabilities"). It bounds writes to the worktree and the state root, never a path inside the worktree.
- The skill edit grants (`docs/security.md`, "Skill edit grants (Claude Code)"; `src/domain/security/skillEditGrants.ts`). This is the inverse case: a path Claude Code protects by itself, opened file by file for a run started with `--allow-skill-edits`. It shows how the Claude adapter writes inline `--settings`, how a plan that declares such a file is refused before the run (exit 11), and how `security.json` records grants for every provider.
- The phase guard (`src/domain/security/phaseGuard.ts`). Inside a phase, phax refuses the phax commands that act on state. It is a guard against mistakes, not a boundary.
- The shell allowlists per provider (`docs/security.md`, "Shell command execution"). Claude allowlists exactly the gate commands. Codex runs anything inside its sandbox. Vibe matches by prefix.
- File reconciliation (`src/domain/reconciliation/`). phax already knows every path a phase created, edited, deleted or renamed. A path a person changed at an interactive stop is a `reviewCorrections` entry, never a deviation.
- The gate's fix loop (`src/domain/gate/fixPrompt.ts`) and what a phase does when the loop is exhausted.

The approach, decided by the operator on 2026-10-29 after a first draft spec that built its own detection, restore and attribution machinery and was abandoned as too complex:
- **Prevention is the providers' own.** Each provider can already refuse a write to a path. phax only carries the project's list from `phax.json` through each adapter into the provider's native configuration. It adds no write interception of its own.
- **One backstop, at the commit.** When a phase commits, phax checks its diff against the list. A phase whose commit would create, change, delete or rename a protected path fails its gate, naming each path. That holds whatever wrote the file: an agent's tool, a shell command it ran, a gate step, or a provider in a mode where its native rule does not apply. phax does not restore the file, does not check after every turn, and does not tell a person's change from an agent's.
- **The operator changes protected files outside a run's phases**: on the base branch before the run, between runs, or at an interactive stop, where a person's changes are already `reviewCorrections`. A phase that fails on a protected path is resumed or reset like any phase whose gate failed, once the operator has made or refused the change.

Provider facts, checked in the installed CLIs on 2026-10-29. Re-check each in the installed source or binary before writing it into the spec, and say which you checked:
- **Claude Code 2.1.312.** `permissions.deny` rules in the inline `--settings` object. Only `Edit(<pattern>)` rules are matched for file writes, and they cover every file-editing tool: Edit, Write, MultiEdit, NotebookEdit. `Write(...)` and `MultiEdit(...)` rules never match. A pattern without a leading slash is gitignore-style, relative to the session's working directory. `//<path>` is absolute; a single `/` anchors to the settings file's location, which for inline settings is a temp file. Deny rules hold in headless `-p` and under `acceptEdits`, but not under `bypassPermissions`, which is phax's unsafe mode. Bash `>` redirects are checked against deny rules; `sed -i`, `cp` and scripts are not. Today phax passes `--settings` only when skill edit grants exist (`src/infra/providers/claudeSkillEditSettings.ts`, `claudePermissionFlags.ts`), so the deny rules must merge into that object.
- **Mistral Vibe 3.0.3.** The `denylist` key of `write_file` and `edit` in `VIBE_TOOLS`. Unknown keys are silently ignored, so the key name matters. Matching is `fnmatch` against the absolute resolved path. phax already sets `denylist: [<root>/.vibe/**, <root>/.agents/**]` in `src/domain/session/vibeFlags.ts`, and its post-turn read-back of `export.json` compares that list. A phax glob whose fnmatch reading differs from phax's dialect cannot be passed exactly: fnmatch's `*` crosses `/`, and a root-relative pattern never matches an absolute path. For such globs Vibe gets no native rule and relies on the backstop.
- **Codex 0.165.** Permission profiles (`[permissions.<name>] filesystem = { "<abs path>" = "read" }`) can make exact paths read-only inside a writable root, enforced by the OS sandbox and so covering the shell too. Globs support `deny` only, which also blocks reading. Using a profile means replacing phax's `sandbox_mode` `-c` overrides, since the two cannot both be set. Leave Codex on the backstop alone in this spec, say why, and name the profile migration as the later route.

What the spec must cover:
- **Declaring.** A top-level `protectedPaths` list of globs in `phax.json`, in the glob dialect `ArchitectureGlobSchema` already validates (`src/schemas/architecture.ts`); reuse it. Only `phax.json` may set it: a user overlay or `phax.local.json` carrying the key is refused before decode, naming the remedy, as `assignments` is (`src/app/loadConfig.ts`). When `phax.json` declares a protected list, `phax.json` itself is protected too, so a phase cannot empty the list on the run's branch.
- **Native prevention per provider**, from the facts above: what each adapter passes and when (secure mode; read-only sessions need nothing more), and which globs each provider can enforce exactly. Match the globs case-insensitively where the filesystem is case-insensitive, or say why not.
- **The backstop.** Where in the commit path phax checks (`commitPhase` in `src/app/executePlan.ts`), which change kinds count (reconciliation's created, edited, deleted, renamed; a rename touches both paths), and how the failure appears: a failed gate attempt naming each path, with the usual fix loop. The fix prompt says the path is the operator's and the hole must be fixed in code or left failing. When the loop is exhausted, the phase pauses as `gates_exhausted` and the handoff names what is left. The handoff turn runs after the commit (`generatePhaseHandoff`), so say what happens to a protected write it leaves in the worktree.
- **Telling the agent.** The phase prompt names the protected globs and what to do when a hole cannot be fixed: report it in the handoff, never work around it.
- **Recording.** `security.json` moves from version 2 to 3, with a required `protectedPaths` field: `null` when nothing is declared, else the globs and, per provider, `enforced` (a native rule for every glob), `partial` (some globs) or `commit-check-only`. Lift version 2 files with `null`, as version 1 was lifted with `stop: null` (`src/schemas/securityPosture.ts`). This follows the project's rule that new persisted fields are required, not optional.
- **Surface.** The `phax.json` key and its errors, the gate failure line, the fix-prompt section, `security.json`, the `phax.usage.kdl` and CLI reference entries that change, and a "Protected paths" section in `docs/security.md`. An acceptance criterion per behaviour, including:
  - a gate step that writes a protected file;
  - an allowed shell command that writes one;
  - each provider's native rule refusing an edit tool, in the real-CLI e2e suite;
  - a project that declares nothing.

Out of scope:
- detection or restore after each turn;
- telling an operator's change from an agent's;
- a route to change a protected file while a phase is paused;
- plan lint and preflight checks of planned files: a plan that plans a protected file fails at that phase's commit;
- `phax security status` columns and the final-report table;
- Codex permission profiles;
- the commands a project's own tool offers to change such a file (steme's `debt accept`);
- paths outside the worktree;
- what a protected file means.

Constraints:
- Additive: a project that declares no protected path sees no change in behaviour, argv, prompts or output. Its `security.json` gains only `protectedPaths: null` at version 3.
- Keep the spec short: the minimal slice above, a handful of requirements, and only genuine §9 questions, each with its options, what each abandons and a recommended default.
