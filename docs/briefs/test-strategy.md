Write the phax spec `test-strategy`. A plan's test strategy becomes data: every phase carries a list of guarantee lines, each placed on four closed coordinates, and phax can show a plan whole, before it runs, as one overview that says what each phase builds, with which model, which part of the architecture it touches, and which guarantees test it, frozen as oracles or written in the phase.

Why: today `testStrategy` is a free string in the plan document (`src/schemas/planDocument.ts`, `Schema.NonEmptyString`) and an informational `### Test strategy` section in plan.md that extraction ignores. Nothing reads it, so nothing can say whether a plan tests what its spec accepts, nor show the operator the plan's shape before `phax run`. `phax run --dry-run` lists execution mechanics (worktrees, commands, security) and `phax plans estimate` its cost; no command answers "lay the plan out for me": phase by phase, inside-out, oracle pairs, test lines, acceptance criteria covered.

What already exists (read it; do not restate it as new):
- **The planning skill's Test strategy section** (`.claude/skills/phax-planning/SKILL.md`, revised in commit a08d93cb): one line per guarantee, `- <guarantee> — <size> · <technique> · <oracle> · <oracle | in-phase>[ · <acceptance criterion id>]`; size is what the test touches (`small` | `medium` | `large`); technique is `example` | `table` | `property` | `metamorphic` | `stateful` | `fuzz` | `contract` | `smoke`; the oracle names what judges the result; the loop is `oracle` (frozen in an oracle pair, the acceptance loop) or `in-phase` (the inner, test-driven loop). Its "What makes a good oracle" subsection and the defaults table by kind of code. This spec turns that prose format into data; it does not re-decide the coordinates.
- **The plan document format**, its renderer (`src/domain/authoring/renderPlan.ts`, `section("Test strategy", phase.testStrategy)`), the headless plan authoring prompt and its JSON Schema, and `phax artifact migrate-documents` with the frozen-snapshot mechanism.
- **The deterministic plan.md parser** shared by `phax plans lint`, `phax plans estimate` and extraction, and `phax-plan.json`, which today carries no test strategy.
- **Oracle phases** (`docs/specs/archive/2610201518-oracle-phases.md`): the `oracle` key `{ dischargedBy, files }`, the `oracles` check shared by lint and the run preflight.
- **The spec document's acceptance criteria** (`src/schemas/specDocument.ts`): each has an `id`; a plan's `source-spec` names its spec.
- **The architecture provider and assignment bounds** (`phax architecture`, `src/schemas/architecture.ts`): a report's parts, each with globs; without a provider, `phax architecture` exits 1 with one line.
- **`phax plans estimate`** (P10/P50/P90 per phase, a verdict on the subscription windows) and **`phax run --dry-run`**.

What is settled (the operator's direction of 2026-10-23 and the repository's standing rules; do not reopen):
1. **The four coordinates are closed enums**, one per coordinate (explicit per-variant enums, never a permissive superset): size, technique and loop are closed literals; the oracle is a non-empty string; the acceptance criterion id is optional per line. No optional field for older sidecars beyond what the format itself declares (no back-compat shims in persisted formats).
2. **Oracle pairs and test lines agree.** A line in the `oracle` loop belongs on an oracle phase; a discharging phase lists only its own `in-phase` lines.
3. **The overview is read-only and model-free.** It reads the plan with the deterministic parser, never a model, and it starts no session and writes nothing. It runs before approval as well as after, like `phax plans lint`.
4. **The overview shows, per phase in plan order:** id and title, model and effort, mode, oracle role (oracle phase, discharging phase, or none), the architecture parts its planned files fall in when an architecture provider is configured (its planned files otherwise), and its test lines. At the end, for a plan with a source spec: each acceptance criterion and the lines that name it, and the criteria no line names.
5. **The planning skill is revised with the format**: the line format becomes the field's description, the Test strategy section points to the data, the headless section documents the new shape.

Settle in §9, framing each option by what it abandons:
- **Where the structure lives.** Only in the plan document (headless plans get it; a hand-authored plan.md shows nothing in the overview), or also parsed from the `### Test strategy` lines of any plan.md by the deterministic parser, and whether it then joins `phax-plan.json` or stays out of the run's extracted plan.
- **What `migrate-documents` writes for a live plan sidecar whose `testStrategy` is a string.** It is deterministic and cannot invent coordinates. For instance: refuse and name re-authoring; lift into one line marked as unstructured that lint reports; or parse the string when it already follows the line format and refuse otherwise. Name what each costs the live plans (`interactive-phases`).
- **What lint holds.** Which of these are errors, warnings, or not checked: an acceptance criterion of the source spec named by no line; a line naming a criterion id the spec does not have; an `oracle` line on a phase that is not an oracle phase; an oracle phase with no `oracle` line; a phase with no line at all (a docs-only phase may test nothing).
- **The overview's command and contract.** A new `phax plans overview <plan>` beside `lint` and `estimate`, or a mode of an existing command; whether it takes `--json` like `estimate`, and whether it folds in the cost estimate or leaves it to `estimate`.
- **How the overview reaches the architecture.** Run the configured architecture provider (a process spawned by a read-only command) or show planned files only and leave the parts to `phax architecture`; what it prints when the provider fails.

Out of scope: the oracles provider changes (failing for the right reason, frozen generators, fixed seeds), which are a separate spec; adding a property-based testing or mutation library to phax's own tests; a graphical view.
