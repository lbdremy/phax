What this plan delivers, all on Effect 3, under the `standard` gate profile, with every test green: the tools and the

Effect 4 and apply the codemod (the phase that records the first counts), then one plan or phase per topic skill, then
the package and the JSON Schemas, then docs, guidance and the removal of the codemod and the reference.

  guides and `v3-to-v4.md` under `migration/`, `LICENSE`, and `SOURCE` naming the tag and commit). It is byte-identical
  to the tag and stays so; `docs/` is outside oxfmt, oxlint does not read Markdown, and the site publishes only the

Deliver, each with its own named tests:
1. **The behaviour corpus** (§4, §5.15, §5.16, §5.19, §5.20): inputs for every persisted format, every frozen decoder,
   every config layer, the spec and plan documents and the provider answers, accepted and refused, captured on
   Effect 3 with their decoded values (JSON-encoded) or refusal lines, and a replay test that passes on Effect 3 and
   that later plans keep unchanged. The corpus exercises every field of every format, which the equivalence check of
   q-snapshots depends on, and a test proves that coverage. Capturing is a script; the captured expectations are
   committed data, never regenerated by a later plan.
2. **The codemod** (§5.2–§5.7): `scripts/` code on ts-morph, pinned with `pnpm add -D --save-exact ts-morph@28.0.0`
   (the one install this plan makes, through the allowed `pnpm add`; the codemod itself fetches nothing at run time),
   run by `pnpm codemod:effect4`, with `--check` and `--ratchet`. Its rule table starts from the spec's §10 list,
   each rule naming the `v3-to-v4.md` line it reads its target from (the vendored file, by line). Fixture tests: one
   input and expected output per rule, a local namesake left untouched, a symbol no rule covers left byte-identical and
   reported under its owning topic skill, a second run that changes nothing. The type-error counts it prints run the
   repository's own type-checks; on this tree they are zero.
3. **The skills** (§5.9, §5.10): `effect4-lookup` and one topic skill per migration area (at least services, errors,
   schema), each stating the files and v3 symbols a phase following it may change, reading only the vendored
   reference and the installed `node_modules/effect` source, naming no clone, fetch or sub-agent.
4. **The `effect-migration` gate profile** in `phax.json` (§5.22, q-green), and where the ratchet keeps the counts the
   previous phase recorded (a committed file the codemod writes, so a phase's gate compares against its base).

Settle in Technical arbitrations, with the dominant loss of each:

skills, then the gate profile, docs last (a short CONTRIBUTING or README note on `pnpm codemod:effect4`, if any).
