Write the phax plan "Backlog fixes — authoring, records, overlap, newer documents". There is no source spec: these are five defects from `NEXT_STEPS.md` § *Small follow-ups* and § *Road to 1.0.0*, each found on a real run and each with a fix already chosen (below). Implement those fixes; do not reopen them.

One phase per defect, in the order below, each green on its own with its tests in the same phase (no oracle phases). Every fix starts with a regression test that reproduces the defect and fails before the change. None of them changes a CLI command, flag, exit code or persisted format.

1. **Headless authoring rejects a document preceded by a sentence.** `src/domain/authoring/jsonText.ts` `stripJsonCodeFence` strips one code fence and nothing else, so a final message like `Ground read. Writing the spec document now.\n{…}` reaches `JSON.parse` whole and `src/app/authorArtifact.ts` (`parseAuthoredDocument`) refuses it as "not JSON" (exit 5, nothing written). Fix in the domain function, which plan extraction (`src/app/extractPlan.ts`) shares: if the fence-stripped text parses, use it; otherwise use the **last** balanced top-level JSON object in the message that parses (a scan that respects string literals and escapes, so braces inside strings do not count). Prose before or after the object, and a fenced object inside prose, are accepted. When there is no such object, the existing "not JSON" refusal and its message are unchanged. Rename the function to say what it now does, and update both callers and their comments.

2. **Authoring records are not auto-pushed.** With `records.autoPush` true, phase records reach the remote through `pushRecordsAtPublish` (`src/app/recordsSync.ts`, called from `src/app/publishRun.ts`), but the records written by headless `artifact new spec|plan` sessions (`writeAuthoringRecord`, called from `recordSession` in `src/app/authorArtifact.ts`) are never pushed; `phax records status` lists them as pending. Fix: after an authoring record is written, push the records branch with the same rules as publish (in-repo destination → the configured publish remote; dedicated `repo` destination → the records clone's `origin`; `records` off or `autoPush` false → no push). A push never fails the authoring command: a failed push becomes a warning beside the existing record warnings (`recordWarning`), saying the record stays pending (`phax records status` lists it) and naming the git push that would share it (remote and branch `phax/records/v1`) — there is no `phax records push` command, and this plan adds none. Factor the push so both callers share it; keep the "at publish" wording only where it is still true.

3. **`plans overlap --landed` cannot read an archived run, and refuses a qualified name.** `src/cli/commands/plansOverlap.ts` decodes `--landed` as a bare short name and resolves it with `resolveRun` (`src/app/resolveRunInfo.ts`), which only looks under `<stateRoot>/runs/`. Once a merged run is archived — the normal next step — the check fails with "No run-status.json", although the archive (see `src/app/archive.ts` for the layout and the registry's `archivePath`) still holds `global-file-reconciliation.json`. Fix: parse `--landed` with `parseRunRef` (`src/domain/runRef.ts`), so `<short>` and `<namespace>.<short>` are both accepted, the namespace defaulting to the configured one; resolve a live run as today, and otherwise an archived run through its registry entry's `archivePath`. A pruned or unknown run fails with a message that says which. The resolution belongs in `app/`, not in the command file; the command keeps parsing and rendering only.

4. **Headless authoring's commit fails under a repo's formatter hook, and the refusal does not say what to do.** In steme-lab a lefthook `oxfmt --check` pre-commit hook rejected the sidecar that phax writes with `JSON.stringify(…, 2)`; phax exited 12 with the plan and sidecar staged and uncommitted, and `ArtifactCommitFailedError` (`src/domain/errors.ts`) only said "commit them manually". phax cannot know a repo's formatter, so the fix is the refusal: when the commit fails, the message names the paths, says that a commit hook (often a formatter) may have rejected them, and gives the remedy — run the repo's formatter on those paths and commit them with the subject phax would have used (print it). State that formatting the sidecar is safe: agreement compares the parsed document, not its bytes (check `src/app/authorArtifact.ts` and the sidecar agreement code, and say so in the message only if it is true). The same error serves every artifact transition (approve, complete, …); word the message so it holds for all of them, and print the intended commit subject from each caller. Exit code 12 is unchanged.

5. **phax rewrites a document written by a newer release.** `src/schemas/persisted.ts` reads a document carrying `$schema` with phax's current decoder whatever release the URL names, as long as the format id matches. After a downgrade, the registry and run/phase status — decoded tolerantly, unknown keys ignored — would be read, stripped of the newer fields, and written back without them: silent data loss. `@lbdremy/phax-schemas` already refuses such a document (`packages/schemas/src/shapes.ts`, `newerReleaseMessage`). Fix: `persisted.ts` refuses, at read, any document whose `$schema` names a release newer than `PHAX_RELEASE` (`src/schemas/release.ts`), with a `PersistedReadError` whose message names the file, the release that wrote it, the running release, and the remedy (upgrade phax). Equal and older releases read as today. Compare releases as semver (major, minor, patch, numerically), not as strings. phax never imports `packages/`: copy the comparison rule, do not import it. Cover every format the bridge reads with one table-driven test.

Technical arbitration already made for defect 5 (record it in the plan's `## Technical arbitrations`): **refuse at read, not only at write** — this gives up running read-only commands (`phax ls`, `phax plans status`, `phax records status`) against a newer document after a downgrade; it is accepted because a downgrade is rare, the remedy is one upgrade, and refusing only writes would need every read to carry its document's release through to the writer.

The prune follow-ups in `NEXT_STEPS.md` are features, not part of this plan.
