# docs.phax.run: the phax documentation site, rendered from the repository and deployed by the release

## 1. Context

phax's documentation lives in the repository as Markdown:

- An 800-line README: install, configure, plans, run, review, persisted formats, troubleshooting, exit codes. It ends with a CLI summary that scripts/docs-cli.ts regenerates between two HTML-comment markers.
- docs/cli/reference.md, generated from phax.usage.kdl by the usage CLI and committed.
- docs/security.md and docs/release.md.
- docs/model-catalog.md, generated and committed.
- One blog post, docs/blog/announcing-phax-1.0.md, written ahead of a 1.0 that has not shipped: the CLI is at 0.17.0 and 'Road to 1.0.0' lists open blockers.
- Two comparisons under docs/comparisons/.

The sources link to each other by repository path (docs/cli/reference.md#phax-orient, ./spec-kit-vs-phax.md) and to in-page anchors (#security-modes). They also link to files that are not user documentation (docs/model-routing.md, docs/ideas/desktop-app.md, .claude/skills/phax-planning/SKILL.md).

Since 0.17.0, every document phax writes starts with `$schema: https://docs.phax.run/schemas/<format id>/<release>.json` (the schemas-package spec, Completed). The JSON Schema of each shape is committed as packages/schemas/snapshots/<format id>/<shape release>.schema.json. Each format also has one pre-schema snapshot and, between releases, a next snapshot. A shape is named by the release that first wrote it, so a release that leaves a format's shape unchanged adds no snapshot for that format. Today 15 formats each have a pre-schema and a 0.17.0 snapshot. Apart from the current version, nothing in the tree lists the releases cut since 0.17.0.

The release workflow is one job on v* tags. In order, it:
1. runs the gate;
2. builds four binaries;
3. smoke-tests the schemas tarball;
4. checks both npm manifests against the tag;
5. stage-publishes @lbdremy/phax-schemas, then @lbdremy/phax;
6. creates the GitHub Release.
A unit test pins that every step that can fail runs before the first publish. CI builds and tests every push to main and every pull request, and deploys nothing.

On 2026-09-25 the author decided that docs.phax.run is a rendering of these sources: built with Rspress v2 from a site/ folder, deployed on the release tag to Cloudflare Workers Static Assets.

Ground read:

- `NEXT_STEPS.md` — 'The docs site, in the release pipeline' was decided with the author on 2026-09-25. docs.phax.run is a rendering of the README, docs/cli/reference.md, security.md, release.md, the model catalog and docs/blog/. It is built with Rspress from a site/ folder that is neither an app nor a workspace package, and deployed on the release tag. Hosting is Cloudflare Workers Static Assets: a wrangler.jsonc whose assets.directory is the Rspress output, no Worker script, preview URLs per version. steme copies the pipeline afterwards; www.phax.run and app.phax.run live in phax-cockpit. 'Road to 1.0.0': 1.0 has not shipped and its blockers are open, ordered by 'what 1.0 would be lying about'.
- `README.md` — About 800 lines: an untitled intro, then 31 `##` sections, ending with 'CLI command reference', a summary scripts/docs-cli.ts regenerates between HTML-comment markers. It links to docs/cli/reference.md#phax-orient and docs/security.md#shell-command-execution, to in-page anchors (#security-modes, #configure) and to files that are not user docs (docs/model-routing.md, docs/state-machine.md, docs/observability.md, docs/e2e-testing.md, docs/plan-extraction-model.md, .claude/skills/phax-planning/SKILL.md, examples/hello-world/plan.md). - `docs/blog/announcing-phax-1.0.md, docs/comparisons/*.md` — One post announcing 1.0, which has not shipped (no frontmatter, no date). Two comparisons, which link to each other (./spec-kit-vs-phax.md) and to docs/ideas/*.md, which the site will not render.
- `package.json, pnpm-workspace.yaml` — Version 0.17.0. check:full = typecheck, unit, integration, type tests, lint, format check, architecture audit, knip, model-catalog check. The workspace file declares no packages; packages/schemas is built by root scripts.

## 2. Problem

docs.phax.run does not exist, yet phax 0.17.0 already writes its URLs into every document. The `$schema` of a run status, a record manifest or an approvals ledger points at a host that answers nothing. An editor or validator cannot resolve the schema a document names, and the schemas-package promise ('the URL serves that release's JSON Schema of the format') is not kept.

A site that served only the snapshots on disk would still be wrong after the next release. A format whose shape did not change has no snapshot named for that release, so its URL would 404 for every document that release writes. A Cloudflare deploy replaces the whole asset set, so one deploy of an older tag, or a build from a clone without tags, would silently remove URLs that existing documents depend on.

For readers, the documentation is one long README on GitHub. It has no navigation and no search, its links point at repository paths, and the CLI reference is reachable only as a raw generated Markdown file.

Building the site the usual way, with its own copy of the guide, would create a second source that drifts from the README the first time either is edited. Phases edit the README, the reference and the catalog all the time.

The site also has no identity: no colours, no logo, no favicon. The brand rules exist only in a private corpus this public repository cannot link to.

## 3. Product goal

The release workflow publishes docs.phax.run as a deterministic, offline rendering of the documentation the repository holds at the release tag:

- the README, split into guide pages by a committed page map;
- the CLI reference, security, release and the model catalog;
- the comparisons, and each blog post once the release it names has shipped.

Links are rewritten to site routes and checked. The site has a dark-first phax identity. Every released format's JSON Schema is served at the exact `$schema` URL phax writes, for every release, forever. CI builds the site on every change; only a release, or the author by hand, deploys it.

> docs.phax.run is the repository at the release tag, rendered: the site adds a page map and an identity, never a second copy of the content, and a schema URL, once served, is served forever.

## 4. Terminology

- **Source** — A committed Markdown file the site renders: README.md, docs/cli/reference.md, docs/security.md, docs/release.md, docs/model-catalog.md, docs/blog/*.md or docs/comparisons/*.md.
- **README section** — The text of README.md from one `##` heading up to the next. The intro is the text before the first `##`.
- **Page map** — The single committed file under site/ that assigns every README section and every other source to a route, to `omit`, or to a hold.
- **Route** — A path on the site, such as /guide/run.
- **Hold** — A page-map entry that keeps a source off the site until a named release. A build for an earlier release neither renders that source nor links to it.
- **Release ledger** — The committed, append-only list of every release cut since the first supported release (0.17.0). The release cut appends to it.
- **Served schema** — The file at /schemas/<format id>/<release>.json: for that release, the format's latest release-named snapshot whose shape release is at or before it.
- **Schema index** — /schemas/index.json: the list of every served schema path in a build. The deploy guard reads the live copy.
- **Deploy guard** — The check, run before any upload, that the new build serves every path listed in the live schema index.
- **Preview URL** — The Cloudflare Workers URL of one uploaded release, aliased by that release (for example v0-18-0). It keeps serving that release's site after later releases are promoted.
- **Promote** — Make an uploaded version the one docs.phax.run serves.
- **Identity tokens** — The colour values of the site theme (Rspress `--rp-c-*` variables), one set per theme.
- **Gold accent** — The theme's brand token: an old gold, deep and unsaturated, never yellow and never a gradient. It is used only for rules, focus rings, the logo and highlights.
- **Shape release, snapshot, format id, first supported release** — As defined by the schemas-package spec.

## 5. Functional requirements

### 5.1 Rendered from the repository's own sources

The site build shall take every page's content from the committed sources as they are (README.md, docs/cli/reference.md, docs/security.md, docs/release.md, docs/model-catalog.md, docs/blog/*.md and docs/comparisons/*.md), with no copy of their content committed anywhere else.

### 5.2 One page map

The site build shall build the page tree from one committed page map that assigns each README section, and each other source file, to exactly one of: a route, `omit`, or a hold until a named release.

### 5.3 Nothing silently dropped

IF a README section or a source file is absent from the page map, or the page map names a heading or file that no longer exists, THEN the site build SHALL fail, naming that section or file.

### 5.4 Rendered as GitHub renders it

The site build shall render every source as GitHub-flavoured Markdown: angle-bracket placeholders and braces outside code appear as written, and HTML comments are dropped.

### 5.5 Links between sources become site links

WHEN a source links to a rendered source, with or without an anchor, THE site build SHALL rewrite the link to the route and anchor where that content is served.

### 5.6 Links to unrendered files go to GitHub at the tag

WHEN a source links to a repository file the site does not render THE site build SHALL rewrite the link to that file on GitHub at the release tag the site is built for.

### 5.7 A broken link fails the build

IF a relative link names a file that does not exist in the repository, or an anchor its target page does not have, THEN the site build SHALL fail, naming the source file, the line and the link.

### 5.8 Held sources stay off the site

WHERE the page map holds a source until a release THE site SHALL neither render nor link to that source in a build for an earlier release.

### 5.9 Offline build, self-hosted assets

The site build shall complete without network access, and the built pages shall load no font, script, style or image from another origin.

### 5.10 Deterministic

The site build shall produce byte-identical generated page sources and schema files from the same commit.

### 5.11 Generated, never committed

The site build shall write its generated sources and its output only to paths the repository ignores.

### 5.12 Every release's schema at its `$schema` URL

For each release in the release ledger, and each format with a released shape at or before that release, the site shall serve at /schemas/<format id>/<release>.json the bytes of that format's latest release-named snapshot whose shape release is at or before that release.

### 5.13 No unreleased shapes

The site shall serve no pre-schema snapshot and no next snapshot.

### 5.14 Schema response

WHEN a served schema URL is requested THE site SHALL answer 200 with Content-Type application/json and Access-Control-Allow-Origin *.

### 5.15 The release cut records the release

WHEN the release cut cuts release X THE release cut SHALL append X to the release ledger in the release commit.

### 5.16 Ledger agrees with the tree

IF the release ledger's last entry differs from the root package.json version, or a release-named snapshot names a release absent from the ledger, THEN the site build SHALL fail, naming the mismatch.

### 5.17 A served schema is never removed

IF a build does not serve a path listed in the live schema index THEN the deploy SHALL refuse before uploading anything, naming the first missing path.

### 5.18 Latest release only

The site at docs.phax.run shall present only the documentation of the release it was built from, with no version switcher and no route prefixed by a version.

### 5.19 The release is shown

The site shall show in its top navigation the release it was built from, as vX.Y.Z, linking to that release on GitHub.

### 5.20 A preview URL per release

WHEN the release workflow deploys release X THE deploy SHALL publish X's site at a preview URL named for X that keeps serving X's site after later releases are promoted.

### 5.21 Deploy after every check, before any publish

WHEN a release tag is pushed THE release workflow SHALL deploy the site only after every gate, build, smoke and version check has passed, and before the first npm stage publish.

### 5.22 A failed deploy leaves nothing behind

IF the deploy guard, the upload or the preview check fails THEN the release workflow SHALL stop with no npm package staged, no GitHub Release created, and the previously promoted site still serving docs.phax.run.

### 5.23 CI builds the site

WHEN a commit is pushed to main or a pull request is opened or updated THE CI workflow SHALL build the site.

### 5.24 Only the deploy holds the credential

The Cloudflare deploy credential shall be referenced only by the deploy steps of the release workflow and of the manual deploy, never by the CI workflow, a phase or a repository script.

### 5.25 Explicit author redeploy

WHERE the author redeploys a released tag by hand THE manual deploy SHALL build that tag and run the same guard, preview upload, check and promotion as the release workflow, staging nothing on npm.

### 5.26 The project gate builds the site

WHEN `pnpm check:full` runs THE project gate SHALL run `pnpm site:build` and fail when it fails.

### 5.27 One-time setup is documented, by hand

The release documentation shall list, as steps the author performs by hand and never automated: the Cloudflare account with the phax.run zone, the API token and the account id as GitHub secrets, the docs.phax.run custom domain with its DNS record, and preview URLs enabled.

### 5.28 Dark first

WHEN a visitor with no stored theme preference opens the site THE site SHALL render the dark theme.

### 5.29 Contrast thresholds

In both themes, the identity tokens shall give these minimum contrast ratios against every background token they are used on: running text and links 7:1, secondary text 4.5:1, gold accents 3:1.

### 5.30 Gold is an accent in the light theme

WHILE the light theme is active THE site SHALL use gold only for accents (rules, focus rings, the logo, highlights) and the bronze link token for links, never gold for running text.

### 5.31 Gold never warns

The site shall render warning, caution and danger callouts in a non-gold hue, never with a gold token.

### 5.32 Logo, wordmark and favicon

The site shall show the phax logo beside the lowercase wordmark `phax`, and shall use the same logo as its favicon. The logo is a single-weight geometric P whose split bowl also reads as an F, in the theme's gold accent, with a bowl gap of at least one eighth of the glyph's height.

## 7. Non-goals

## 8. Acceptance criteria

### The page tree comes from the page map

Given the repository at a commit, with the page map of §6, when `pnpm site:build` runs, then it exits 0, and the output holds one page per mapped route, each with the text of the sources and README sections the map names. The README's generated CLI summary appears on no page. (refs §5.1, §5.2)

### Nothing generated is committed

Given a clean checkout, when `pnpm site:build` runs, then `git status --porcelain` prints nothing, and no committed file under site/ contains a paragraph of any source. (refs §5.11, §5.1)

### An unmapped or vanished section fails the build

Given three variants of the repository: a README with an added `## Contributing` section absent from the page map; a page map still naming `## Locks` after that README heading was renamed; an added docs/blog/second-post.md absent from the map, when `pnpm site:build` runs on each, then each run exits non-zero, naming `Contributing`, `Locks` and docs/blog/second-post.md respectively. (refs §5.3)

### A heading rename fails the phase that made it

Given a phase that renames the README heading `## Run` without touching the page map, when `pnpm check:full` runs in that phase, then it fails, naming `Run`. (refs §5.26)

### Placeholders and comments render as on GitHub

Given a README section whose text holds `<short-name>` and `{#phase-01-setup}` outside code, plus an HTML comment, when the site is built, then the build succeeds, its page shows `<short-name>` and `{#phase-01-setup}` as text, and the comment's text appears nowhere. (refs §5.4)

### Links between sources point to routes

Given the README links `docs/cli/reference.md#phax-orient`, `docs/security.md#shell-command-execution` and `#security-modes`, and the OpenSpec comparison's link `./spec-kit-vs-phax.md`, when the site is built at 0.17.0, then they point to `/reference/cli#phax-orient`, `/security#shell-command-execution`, the route holding the README's Security modes section at that section's anchor, and `/compare/spec-kit-vs-phax`. (refs §5.5)

### Links to unrendered files point to GitHub at the tag

Given the README's link `docs/model-routing.md` and the spec-kit comparison's link `../ideas/desktop-app.md`, when the site is built at 0.17.0, then they point to `https://github.com/lbdremy/phax/blob/v0.17.0/docs/model-routing.md` and `https://github.com/lbdremy/phax/blob/v0.17.0/docs/ideas/desktop-app.md`. (refs §5.6)

### A broken link fails the build

Given a fixture source linking `docs/missing.md`, and another linking `docs/cli/reference.md#phax-no-such-command`, when `pnpm site:build` runs, then it exits non-zero and names each source file, line and link. (refs §5.7)

### The 1.0 announcement waits for 1.0

Given the page map holding docs/blog/announcing-phax-1.0.md until 1.0.0, when the site is built at 0.17.0, and again with a fixture version of 1.0.0, then at 0.17.0, no route renders the post, no page links to it, and the navigation has no Blog entry. At 1.0.0, the post is served at its route and Blog appears in the navigation. (refs §5.8)

### Offline build, no remote assets

Given a phase session with no network access, when `pnpm site:build` runs, then it exits 0, and no built HTML, CSS or JS file loads a font, script, style or image from an absolute http(s) URL. (refs §5.9)

### Same commit, same bytes

Given one commit, when `pnpm site:build` runs twice from a clean tree, then the generated page sources and every file under schemas/ are byte-identical between the two runs. (refs §5.10)

### The 15 0.17.0 URLs from the first deploy

Given the release ledger ["0.17.0"] and today's snapshots, when the site is built, then exactly 15 schema files are served, one /schemas/<format id>/0.17.0.json per format id, each byte-identical to packages/schemas/snapshots/<format id>/0.17.0.schema.json; no served path names pre-schema or next. (refs §5.12, §5.13)

### A release without a shape change still serves every format

Given a fixture ledger ["0.17.0", "0.18.0"] in which only registry has a 0.18.0 snapshot and run-status has a next snapshot, when the site is built, then /schemas/registry/0.18.0.json equals the registry 0.18.0 snapshot, /schemas/run-status/0.18.0.json equals the run-status 0.17.0 snapshot, all 15 0.17.0 URLs are still served (30 files in all), and no next snapshot is served. (refs §5.12, §5.13)

### Schemas answer as JSON, cross-origin

Given the built site, when the headers it ships for /schemas/registry/0.17.0.json are read, and the release workflow's preview check requests that release's registry URL, then the headers set Content-Type application/json and Access-Control-Allow-Origin *, and the check passes only on a 200 with that content type. (refs §5.14)

### The release cut appends the release

Given a copy of the tree with the ledger ["0.17.0"], when `pnpm exec tsx scripts/release-cut.ts 0.18.0 --root <copy>` runs, then the ledger is ["0.17.0", "0.18.0"] and its path is among the printed changed paths. (refs §5.15)

### A ledger out of step fails the build

Given two variants: a ledger whose last entry is 0.17.0 under a root package.json at 0.18.0; a snapshot registry/0.18.0.schema.json with 0.18.0 absent from the ledger, when `pnpm site:build` runs on each, then each run exits non-zero, naming the mismatch. (refs §5.16)

### The guard refuses to drop a served schema

Given two fixture live schema indexes: one listing /schemas/registry/0.18.0.json, checked against a v0.17.0 build that lacks it; one answering 404, when the deploy guard runs against each, then against the first, it refuses, naming /schemas/registry/0.18.0.json, and no upload command runs; against the 404 (a first deploy), it passes. (refs §5.17)

### One release, labelled

Given the site built at 0.17.0, when its pages are inspected, then every page's top navigation shows `v0.17.0` linking to https://github.com/lbdremy/phax/releases/tag/v0.17.0, there is no version switcher, and no route begins with a version segment. (refs §5.18, §5.19)

### Upload to a named preview, check, then promote

Given release.yml on tag v0.18.0, when its deploy steps are parsed, then they upload the build with the preview alias `v0-18-0`, check that preview URL, and promote it to docs.phax.run only after the check passes. The release Verify list confirms that, after the next release, the v0-18-0 preview URL still shows v0.18.0. (refs §5.20, §5.22)

### The deploy sits between the checks and the publishes

Given release.yml, when its steps are parsed, then the site build, guard, upload, check and promotion all come after the Gate, binaries, schemas smoke, prepare-npm and version-check steps, and before the first npm stage publish. Only the second publish and the GitHub Release follow the first publish, and no deploy step sets continue-on-error. (refs §5.21, §5.22)

### CI builds, never deploys

Given ci.yml and release.yml, when their steps are parsed, then ci.yml runs `pnpm site:build` after `pnpm build` and has no step that runs wrangler or references a CLOUDFLARE secret; in release.yml, only the deploy steps reference CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID. (refs §5.23, §5.24)

### The author's redeploy runs the same guard

Given the manual deploy workflow, dispatched with tag v0.18.0, when its steps are parsed, then it checks out v0.18.0, runs `pnpm site:build`, the guard, the upload with alias v0-18-0, the check and the promotion, and has no npm publish and no GitHub Release step. (refs §5.25, §5.17)

### One-time setup is written down

Given docs/release.md, when it is read, then a one-time setup section lists the Cloudflare account and phax.run zone, the CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID GitHub secrets, the docs.phax.run custom domain with its DNS record, and enabling preview URLs, and says that none of these steps is automated. (refs §5.27)

### Dark by default

Given the built site and a visitor with no stored preference whose system prefers light, when the home page loads, then the dark theme renders. (refs §5.28)

### Tokens meet their contrast thresholds

Given the theme's identity tokens, when a test computes WCAG 2 contrast ratios for each text, link and accent token against each background token of the same theme, then in both themes, running text and links are at least 7:1, secondary text at least 4.5:1, and gold accents at least 3:1. (refs §5.29)

### Bronze links, no gold text in light

Given the light theme's tokens and styles, when the link colour and the running-text colours are read, then the link colour is the bronze token, and no running-text or link colour is a gold accent token. (refs §5.30)

### Warnings are never gold

Given the theme's styles, when the colours of warning, caution and danger callouts are read, then none is a gold token, and each hue differs from every gold token's hue by at least 20°. (refs §5.31)

### Logo constraints hold

Given the committed logo SVG, when it is parsed and the built pages are inspected, then every stroke has the same width; the logo uses one colour, the accent token, and no gradient; the clear gap between the bowl's two strokes is at least one eighth of the glyph's height. The pages' favicon link references the same SVG, and the navigation shows the wordmark `phax` in lowercase. (refs §5.32)

## 9. Open questions for implementation planning

### Q1 — Should docs.phax.run show only the latest release, or keep older releases browsable (Rspress multiVersion)?

- Latest release only on docs.phax.run; each release's own site stays at its preview URL — abandons: Browsing an older release's docs on docs.phax.run itself. A reader pinned to an older phax uses that release's preview URL, which lives only as long as Cloudflare keeps the version, or GitHub at the tag.
- Rspress multiVersion: one docs tree per kept release, with a version switcher — abandons: The site as a rendering of one commit. Older releases' sources must be kept as copies in the tree, or rebuilt from older tags whose site/ and page map may not exist.

Recommendation: Latest release only on docs.phax.run; each release's own site stays at its preview URL — Decided by the author on 2026-10-04. Older releases' readers need one thing forever, the schema URLs, and those are served for every release whatever the versioning. A 0.x CLI that changes every release is read at its latest. The preview URLs give each release's exact site at no cost, without a second copy of any source.

### Q2 — Where does the build learn which releases' schema URLs to serve? A release that changed no shape leaves no snapshot.

- A committed release ledger, appended by the release cut — abandons: A single record of releases: a second list beside the tags, which must agree with them. The build's ledger-vs-package.json check and the workflow's tag check keep the two in step.
- The repository's v* tags, read at build time — abandons: A build that depends on the commit alone. A shallow or tag-less clone, which is the default CI checkout, builds a site missing every intermediate release, and deploying it would remove URLs.

Recommendation: A committed release ledger, appended by the release cut — Decided by the author on 2026-10-04. Determinism and offline builds are hard requirements, and a tag-dependent build fails both silently. The ledger costs one appended line per release, written by the same cut that renames the snapshots. Its drift is caught offline, because its last entry must equal the package.json version that the workflow already checks against the tag.

### Q3 — Where does the deploy sit relative to the npm stage publishes and the GitHub Release?

- After every fallible check, before the first npm stage publish — abandons: Docs that never run ahead of the packages. The site shows release X while X's packages wait for hand approval, or, if a publish then fails, until the tag is re-pushed.
- Last, after the GitHub Release — abandons: Schema URLs that exist before anything can write them. A failed deploy leaves an approvable release whose documents name URLs that 404, fixed only by a manual redeploy.

Recommendation: After every fallible check, before the first npm stage publish — Decided by the author on 2026-10-04. A 404 on a URL that documents carry breaks a promise. Docs briefly ahead of npm approval break nothing, because staged packages cannot be installed. Deploying before the publishes also keeps the existing invariant intact: every step that can fail precedes the first publish, so a failed deploy stages nothing.

### Q4 — Does the README stay the single source of the guide pages?

- Yes: the page map splits the README by its ## headings — abandons: A site structure of its own. The guide follows the README's order and wording, and README headings become part of the build contract: a rename needs a page-map edit in the same change.
- Move the guide into docs/guide/*.md and slim the README to an overview with links — abandons: The README as the complete manual on GitHub, plus a large content move unrelated to building a site.
- Site-specific copies of the guide under site/ — abandons: A single copy of the content: the copies drift from the README the first time either is edited.

Recommendation: Yes: the page map splits the README by its ## headings — Decided by the author on 2026-10-04. The decision was 'a rendering of what the repo already holds'. The README is what phases edit and what GitHub shows, and the heading contract is enforced mechanically (map-complete, run in check:full), so its cost is visible at the moment it is incurred.

### Q5 — Which identity tokens does the first deploy ship?

- The concrete dark and light tokens of §6, checked by a contrast test — abandons: An identity picked by the author's eye before it goes live. The first palette is derived from the written brand rules. The author may retune the hex values later: the ratios are the contract, not the values.
- The §6 dark tokens only, with no light theme — abandons: Readers who need or prefer a light page (bright rooms, print, low-vision settings), and Rspress's theme toggle.
- Wait for a palette supplied by the author — abandons: A first deploy on the next release. The 0.17.0 schema URLs that documents already carry stay unresolved until the palette exists, or the site ships Rspress's default identity.

Recommendation: The concrete dark and light tokens of §6, checked by a contrast test — Decided by the author on 2026-10-04. The brand rules are precise enough to derive values that pass tested thresholds. A palette is the cheapest part of the identity to change later, and the 0.17.0 URLs should not wait on it.

### Q6 — Who draws the logo and favicon?

- A phase draws a first geometric SVG to the §6 constraints; it is replaced later by swapping the file — abandons: A designer's hand on the first version: the mark is a construction that satisfies the constraints, and will probably be redrawn.
- The author supplies the asset — abandons: An unblocked plan: the phase that wires up the identity waits for a file that does not exist yet.

Recommendation: A phase draws a first geometric SVG to the §6 constraints; it is replaced later by swapping the file — Decided by the author on 2026-10-04. The constraints (one weight, a split bowl, a gap of at least 1/8, single colour) are geometric and testable, so a phase can meet them and the logo test keeps any later redraw honest. Replacing the file changes nothing else.

### Q7 — How is the site checked visually?

- Mechanical checks (contrast, token use, logo geometry, page structure), plus the author's look at `pnpm site:preview` and at the release's preview URL before approving the npm packages — abandons: Automatic detection of a layout regression: a broken layout is caught only when a human looks.
- Screenshot tests against committed baselines, in a headless browser — abandons: A stable gate without network: phase sessions cannot download the browser binary, and font rendering differs between machines, so the baselines flake or get refreshed blindly.

Recommendation: Mechanical checks (contrast, token use, logo geometry, page structure), plus the author's look at `pnpm site:preview` and at the release's preview URL before approving the npm packages — Decided by the author on 2026-10-04. The site's layout is Rspress's, not ours. What this spec adds (tokens, logo, page tree, links) can be checked mechanically. The release already has a human approval point where a glance at the preview URL costs seconds.

### Q8 — Is the 1.0 announcement published on the first deploy?

- Hold it in the page map until release 1.0.0 — abandons: A blog on the first deploy: the Blog section is absent until a post is published.
- Publish it now — abandons: A site that does not lie: docs.phax.run would announce a 1.0 that has not shipped, while Road to 1.0.0 still lists open blockers.

Recommendation: Hold it in the page map until release 1.0.0 — Decided by the author on 2026-10-04. Road to 1.0.0 is ordered by what 1.0 would be lying about, and an early announcement on the official docs would be exactly that. A hold until 1.0.0 publishes the post with the release that makes it true, without a second edit.

### Q9 — Does `pnpm check:full` run the site build?

- Yes, the whole `pnpm site:build` — abandons: A gate as fast as today's: every phase pays the time of the site build.
- CI only — abandons: Catching a README heading rename or a broken link in the phase that made it: the failure appears in CI after the run, outside the fix loop.

Recommendation: Yes, the whole `pnpm site:build` — Decided by the author on 2026-10-04. Phases edit the README and docs constantly. A page-map or link failure is cheap to fix inside the phase's fix loop and expensive to fix after the PR has been opened.

## 10. Implementation-planning note

Settled:

- Decided with the author on 2026-09-25 (NEXT_STEPS): docs.phax.run renders the repository's own sources. It is built with Rspress v2 (@rspress/core) from a site/ folder that is neither an app nor a workspace package, and deployed on the release tag by the release workflow. Hosting is Cloudflare Workers Static Assets: a wrangler.jsonc whose assets.directory is the Rspress output, no Worker script, preview URLs per release. steme copies this pipeline afterwards.

Pre-schema and next snapshots are never served; a served URL is never removed.
- For each release R and each format, the site serves the latest snapshot whose shape release is at or before R. The list of releases is the committed release ledger, appended by the release cut and seeded with 0.17.0 (q-release-list).
- The deploy runs guard → upload with a preview alias → check → promote, after every fallible step and before the first npm stage publish (q-deploy-order). A manual dispatch for a tag is the only other way to deploy.

- The first deploy is the first release tag cut after this work lands, and the 15 0.17.0 URLs resolve from that deploy.
- No source is edited for the site's sake. docs/release.md gains the docs-site steps and the one-time setup because maintainers need them.
- Every §9 question was decided by the author on 2026-10-04, each on its recommended option.

Left open:

- Route and navigation spellings, page grouping and page titles. The §6 tree is indicative; every README section must still map exactly once.
- Whether link rewriting and the dead-link check use Rspress's own features or a pre-build step, provided anchors are checked against the rendered pages.
- The page map's file name and form, the ledger's path, and the exact shape of the schema index.
- The font families (any OFL family installed from npm and self-hosted), and final hex values within the ratio thresholds.
- Whether the custom domain is declared in wrangler.jsonc or attached once by hand, and how the preview URL's account subdomain reaches the check step.
- Whether a PNG favicon is added as a fallback beside the SVG.
- Whether the manual deploy is a separate workflow or a dispatch trigger on the release workflow.

Constraints:

- No CLI change and no change to any persisted format phax writes. Served schemas are the snapshots, byte for byte, with no $id injected.
- The build runs offline. Dependencies come from the lockfile install, fonts from npm packages, and docs/cli/reference.md and docs/model-catalog.md are used as committed: no usage CLI and no catalog regeneration in the site build.
- site/ has no package.json. @rspress/core, wrangler and the font packages are root devDependencies. knip, oxlint, oxfmt and vitest must ignore the generated directories and treat the site config as an entry point.
- Verify how Rspress v2 compiles .md files (MDX or plain Markdown). The README and reference.md contain angle-bracket placeholders, braces and HTML comments that MDX would reject (§5 gfm).
- The release workflow keeps its invariants: every step that can fail precedes the first npm stage publish, and only the second publish and the GitHub Release follow it. tests/unit/releaseWorkflow.test.ts is extended, not loosened. The Cloudflare secrets appear only in the deploy steps' env; the npm rule (GITHUB_TOKEN only, no NPM_TOKEN) is unchanged.
- No deploy from CI, from a phase or from a local script, and no deploy credential in the repository.
- Nothing from ~/.phax, the private phax-cockpit corpus or any other repository enters this repository. The brand rules are restated in this spec, not linked.
- Tests use no network. The deploy guard is tested against a fixture live index; only the release workflow and the manual deploy touch the network.
- Keep the pipeline plain and copyable for steme: phax-specific values are limited to the Worker name, the domain and the sources. Do not parameterise anything for steme.
