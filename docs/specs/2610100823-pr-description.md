# Short pull request description

## 1. Context

When `phax publish-pr <run>` (or `publish.auto`) opens a pull request, phax writes the PR description from the run's review inputs. Today that description is the review handoff with a header in front of it: `# PHAX Run Review Handoff`, `Generated by PHAX.`, then the full `review-handoff.md` content, which opens with its own `# Run Review Handoff`. The handoff holds the run summary, the source-spec outcome, the global file reconciliation (planned, edited and optional file lists), the global unplanned and missing changes, the attention points, the unexplained deviations, the full plan compliance review, the `## Review notes` section, and then, for every phase, its whole file reconciliation and its whole phase handoff ("What was delivered", "Key decisions and why", "Exact locations", "What the next phase needs to know"). When the result passes 60000 bytes, phax cuts it from its end and appends a note saying the full handoff is in `review-handoff.md` on the PR branch. The exact body is written to `pr-body.md` in the run folder before `gh pr create` reads it. `review-handoff.md` itself lives in the run folder (`~/.phax/runs/<namespace>.<name>/`), where the review-code session and `phax review-handoff` use it; it is never committed to the run's branch.

Ground read:

- `src/domain/publish/body.ts` — Today's PR body: a fixed `# PHAX Run Review Handoff` header plus the whole review handoff, cut from its end at 60000 bytes, with a truncation note claiming `review-handoff.md` is on the PR branch.
- `src/app/publishRun.ts` — publish-pr rebuilds the review handoff (with the compliance review markdown), passes it to the body builder, writes `pr-body.md` to the run folder and hands that file to `gh pr create`; an existing PR is reused and its body left alone.
- `src/app/reviewHandoff.ts` — buildReviewHandoffContent: `# Run Review Handoff`, run summary, source spec, global reconciliation, unplanned, missing, attention points, unexplained deviations, plan compliance review, review notes, then per-phase file reconciliation and full phase handoff.
- `src/app/loadReviewHandoffInputs.ts` — The shared inputs: global reconciliation, per-phase contents, source-spec outcome fragment, review notes from each phase's last gate attempt.
- `src/domain/review/reviewNotes.ts` — Review notes are grouped by owner, listed once per distinct text with their phases, under one `## Review notes` section with a fixed intro line.
- `src/schemas/complianceReview.ts` — The recorded compliance review carries a run verdict, a per-phase verdict with findings, and a list of attention points.
- `src/app/finalReview.ts` — Opening final review writes `review-handoff.md` and `final-report.md` into the run folder; the review-code session and `phax review-handoff` read it there.
- `src/schemas/status.ts` — A run records its plan's repo-relative path, except for a loose plan, which has none.
- `docs/specs/archive/2610091304-guarantee-reports.md` — §5.36–§5.39: review notes gathered into one `## Review notes` section, grouped by owner, listed once, placed so a truncated body keeps them, never sent to an agent.
- `README.md` — Publish section: the compliance verdict goes into the PR description; review notes go into the review handoff and the PR body; run folders live under `~/.phax/runs/<namespace>.<name>/`.

## 2. Problem

The PR description is too long to read, and most of it is not for the person reading it. The guarantee-reports run's PR #129 description was 59387 bytes over 947 lines, at the cap. A reviewer has to scroll past about 150 lines of file lists, then a file reconciliation and a full handoff for every phase, much of it written for the next phase's agent, then a compliance review whose per-phase findings repeat those handoffs. There are also two top-level headings. What the reviewer has to act on (whether the run did what it set out to do, the deviations nobody explained, the compliance verdict and its attention points, the gate steps' review notes) is buried in the rest. The truncation note is also wrong: it points to `review-handoff.md` on the PR branch, but the file is only in the run folder on the machine that ran it, so a reader who follows it finds nothing.

## 3. Product goal

The PR description becomes its own short document. phax builds it from the same inputs as the review handoff, but it holds only what a reviewer acts on: what the run set out to do and whether it did it, what needs the reviewer's judgement, and a correct pointer to the full detail. The review handoff stays the full record in the run folder, unchanged.

> Give the reviewer only what they act on, and point to the rest; anything else is too much information.

## 4. Terminology

- **PR body** — The pull request description phax writes when it creates a run's pull request, also saved as `pr-body.md` in the run folder.
- **review handoff** — `review-handoff.md` in the run folder: the full review record of a run. This spec does not change it.
- **run folder** — The run's state directory on the machine that ran it, `~/.phax/runs/<namespace>.<name>/` by default. It is not on the run's branch.
- **deviation** — A file the run touched that its phase did not plan (unplanned), or a file a phase planned that the run never touched (missing: a promise the run did not keep), as the global file reconciliation records them.
- **unexplained deviation** — A deviation whose path does not appear in the phase handoff of any phase it is attributed to (the phases that touched an unplanned file, or planned a missing one). This is the test the review handoff already applies.
- **phase compliance verdict** — The verdict the recorded compliance review gives one phase: `conformant`, `conformant-with-deviations` or `divergent`.
- **shortening** — Cutting entries from the PR body's cuttable lists so that the body fits the size cap.

## 5. Functional requirements

### 5.1 The PR body is its own document

The system shall build the PR body from the run's review inputs as its own document, holding only the run summary, `## Phases`, `## Needs your review`, `## Review notes` when there are notes, and `## Full detail`, in that order.

### 5.2 No full-record material in the PR body

The PR body shall carry no file reconciliation, no phase handoff text, no compliance review summary and no compliance finding.

### 5.3 No top-level heading

The PR body shall carry no top-level (`# `) heading.

### 5.4 Run summary

The PR body's run summary shall name the run's qualified name, its plan path (or `loose plan` when the run recorded none), the source-spec outcome when the run stated one, its gate profile, its count of passed phases out of all phases, its verified surfaces, and the run's compliance verdict (or `not reviewed`).

### 5.5 One line per phase

The `## Phases` section shall hold one line per phase, in plan order, giving the phase id, its title, its phase compliance verdict (or `not reviewed`), and its count of deviations with how many are unexplained, or `skipped` in place of the verdict and counts for a skipped phase.

### 5.6 Unexplained deviations need the reviewer

The `### Unexplained deviations` subsection of `## Needs your review` shall list every unexplained deviation, with its path, its kind (unplanned or missing) and the phases it is attributed to, or `None.` when there is none.

### 5.7 Compliance attention points

WHERE the run has a recorded compliance review THE system SHALL list that review's attention points verbatim under `### Compliance attention points` in `## Needs your review`, or `None.` when the review has none.

### 5.8 No compliance review recorded

IF the run has no recorded compliance review THEN the PR body SHALL show `not reviewed` as the run's and every phase's compliance verdict, and carry no `### Compliance attention points` subsection.

### 5.9 Review notes keep their place and guarantees

WHEN at least one review note was gathered from the phases' last gate attempts THE system SHALL place the `## Review notes` section, rendered exactly as the review handoff renders it, between `## Needs your review` and `## Full detail`.

### 5.10 Pointer to the full detail

The `## Full detail` section shall name the review handoff's path in the run folder, with the user's home directory written as `~`, and the `phax review-handoff <run>` command that writes it again.

### 5.11 Pointer to the records

WHERE records are configured for the repository THE system SHALL name `phax records explain <commit>` in `## Full detail` as the way to read a phase commit's prompt, diff, gates and handoff.

### 5.12 No false location

The PR body shall never say that the review handoff is on the PR branch.

### 5.13 Size cap and what is cut first

IF the PR body would exceed 60000 bytes THEN the system SHALL cut list entries from the end of `### Unexplained deviations` first, then from `### Compliance attention points`, then from `## Review notes`, until the body fits, replacing each run of cut entries with one line that counts them and never cutting the `## Review notes` heading or its intro line.

### 5.14 A shortened body says so

WHEN the PR body was shortened THE system SHALL end it with a note saying that it was shortened to fit GitHub's limit and that the review handoff named in `## Full detail` holds every entry.

### 5.15 pr-body.md is the body sent

WHEN publishing creates a pull request THE system SHALL write the PR body to `pr-body.md` in the run folder, byte for byte as given to GitHub, before creating the pull request.

### 5.16 The review handoff is untouched

The review handoff written to the run folder shall keep every section it holds today, whatever the PR body holds.

## 7. Non-goals

- Changing `review-handoff.md`: its sections, order and content stay as they are, as do the readers of the file (the review-code session, `phax review-handoff`).
- Changing what review notes are, how they are gathered or grouped, or the guarantee that none reaches an agent (guarantee-reports §5.36–§5.39).
- Updating the description of a pull request that already exists for the run's branch: reuse keeps today's behavior and leaves its body alone.
- Committing the review handoff, or any other run-folder file, to the run's branch.
- Changing the PR title, the push, the base-branch choice, or `publish.auto`.
- Running the compliance review as part of publishing, or waiting for one: phax stays autonomous, and nothing here stops a run or a phase.
- Changing how deviations are detected or when one counts as explained.

## 8. Acceptance criteria

### The body is short and holds no full-record material

Given a made-up three-phase run `acme.greet-cli` at review_open whose phases each have a file reconciliation and a phase handoff with a "Key decisions and why" section, and a recorded compliance review with a summary and per-phase findings, when `phax publish-pr greet-cli` creates the pull request, then the body holds, in order, the run summary, `## Phases`, `## Needs your review` and `## Full detail`; it holds no line starting with `# `, no `## Phase details`, no `File reconciliation` heading, no `## Plan compliance review`, no `Global File Reconciliation`, no line of any phase handoff, neither the compliance summary nor any finding message, and no shortened note. (refs §5.1, §5.2, §5.3)

### The summary says what the run did

Given the run's plan path recorded as `docs/plans/2610101200-greet-cli-plan.md`, its spec completed on the branch, 3 of 3 phases passed, verified surfaces local and structural, gate profile `standard`, and a recorded compliance verdict `conformant-with-deviations`, when the pull request is created, then the run summary names `acme.greet-cli`, the plan path, the spec outcome line, `standard`, `3/3`, `local, structural` and `conformant-with-deviations`; for the same run created from a loose plan, it shows `loose plan` instead of a path. (refs §5.4)

### One line per phase

Given phase-02 with one explained unplanned file and one unexplained one, and phase verdict `conformant-with-deviations`, and phase-03 skipped, when the pull request is created, then `## Phases` holds three lines in plan order; phase-02's line gives `phase-02`, its title, `conformant-with-deviations`, 2 deviations and 1 unexplained; phase-03's line gives its id, its title and `skipped`. (refs §5.5)

### Only unexplained deviations are listed

Given unplanned `src/render/colors.ts`, touched in phase-02 and absent from its handoff; missing `tests/render/plain.test.ts`, planned in phase-02, untouched and absent from its handoff; and unplanned `src/render/index.ts`, named in phase-02's handoff, when the pull request is created, then `### Unexplained deviations` lists `src/render/colors.ts` as unplanned in phase-02 and `tests/render/plain.test.ts` as missing in phase-02, and does not list `src/render/index.ts`. (refs §5.6)

### No deviation says None

Given a run with no unexplained deviation, when the pull request is created, then `### Unexplained deviations` holds `None.`. (refs §5.6)

### Attention points reach the reviewer

Given a recorded compliance review with two attention points and findings for two phases, when the pull request is created, then `### Compliance attention points` lists both attention points verbatim, and no finding message appears in the body. (refs §5.7, §5.2)

### No compliance review says not reviewed

Given a run with no recorded compliance review, when the pull request is created, then the run summary and every non-skipped phase line show `not reviewed`, and the body has no `### Compliance attention points`. (refs §5.8)

### Review notes keep their section

Given phase-02 and phase-03 whose last gate attempts each left the note `The greeting copy changed; check it with the docs owner.` with owner `design-review`, and phase-01, whose attempt 1 left a note that its last attempt did not, when the pull request is created, then `## Review notes` appears after `## Needs your review` and before `## Full detail`, with the intro line `Notes the gate steps left for a person. None was sent to the agent.`, a `### design-review` group, the note listed once naming phase-02 and phase-03, and no text from phase-01's attempt-1 note. (refs §5.9)

### No note, no section

Given a run whose phases' last gate attempts left no review note, when the pull request is created, then the body has no `## Review notes`. (refs §5.9)

### The pointer is true

Given the run folder `<home>/.phax/runs/acme.greet-cli/`, when the pull request is created, then `## Full detail` names `~/.phax/runs/acme.greet-cli/review-handoff.md` and `phax review-handoff greet-cli`, the body contains no absolute home-directory path, and no text in the body says that `review-handoff.md` is on the run's branch or on any branch. (refs §5.10, §5.12)

### Records are named only when configured

Given one repository with records configured and another without, when each publishes the same made-up run, then the first body's `## Full detail` names `phax records explain <commit>`, and the second does not. (refs §5.11)

### Over the cap, review notes survive

Given a made-up run with 2000 unexplained deviations, 30 compliance attention points and five review notes, whose full body would exceed 60000 bytes, when the pull request is created, then the body is at most 60000 bytes; deviation entries are cut from the end first and replaced with one line counting them; the attention points are cut only if the cut deviations are not enough; all five review notes are present; and the body ends with the shortened note naming the review handoff. (refs §5.13, §5.14)

### Notes are cut last and keep their heading

Given a made-up run whose review notes alone exceed 60000 bytes, when the pull request is created, then the body is at most 60000 bytes; no deviation or attention point entry remains; `## Review notes` and its intro line are present, followed by the first notes and a line counting the cut ones; and the body ends with the shortened note. (refs §5.13, §5.14)

### pr-body.md is what GitHub got

Given a run with no existing pull request for its branch, when `phax publish-pr greet-cli` creates the pull request, then `pr-body.md` in the run folder exists before `gh pr create` runs and is byte-identical to the body file given to it. (refs §5.15)

### The review handoff keeps its detail

Given the run from "The body is short and holds no full-record material", when the pull request is created, then `review-handoff.md` in the run folder still holds `## Phase details`, each phase's file reconciliation and its phase handoff, and the global file reconciliation. (refs §5.16)

## 9. Open questions for implementation planning

### Q1 — Should the PR body carry the compliance review's one-paragraph summary next to the run verdict?

- Verdict and attention points only — abandons: the reviewer's one-paragraph reason for the verdict without opening the review handoff
- Also the compliance summary paragraph — abandons: the governing rule: a paragraph the reviewer reads but does not act on, which in practice restates the attention points and the phase verdicts

Recommendation: Verdict and attention points only — The attention points are the compliance reviewer's distillation of what a person must look at. The summary explains the verdict without adding anything to act on, and it stays one link away in the review handoff. Losing it costs a click; keeping it brings back the restating the brief complains about.

## 10. Implementation-planning note

Settled:

- The PR body is a new document built from the review handoff's inputs: global reconciliation, phase contents (used only to decide whether a deviation is explained), source-spec outcome, review notes, the recorded compliance review, and the run's verified surfaces. It is no longer the handoff with a header.
- Sections and order are as in §6 and are normative; line wording is indicative.
- The compliance verdict, per-phase verdicts and attention points come from the recorded structured compliance review, not from its markdown.
- The 60000-byte cap stays; the cut order is unexplained deviations, then attention points, then review notes; the summary, the phase lines and `## Full detail` are never cut.
- The pointer names the run-folder path with `~` for the home directory and `phax review-handoff <run>`; `phax records explain` appears only where records are configured. The false "on the branch" claim goes.
- `pr-body.md` keeps its name and place, and holds the exact body sent.
- `review-handoff.md` and its builder are untouched in behavior.

Left open:

- Exact line wording of the summary, the phase lines, the count line for cut entries, and the shortened note.
- How the per-phase deviation counts are derived from the global reconciliation's phase attribution, as long as an unexplained deviation counts once against each phase it is attributed to.

Constraints:

- Respect the layers: the body is built in the domain from decoded inputs; reading the run folder stays in the app layer through the FileSystem port.
- No back-compat shims: the old header and truncation note are removed, not kept behind a switch.
- Fixtures and examples are made up; none copies a real PR body.
- The PR body is generated, never hand-edited.
- Nothing in publishing sends a review note, or the PR body, to an agent.
