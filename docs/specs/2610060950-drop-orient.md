# Drop orient: phax stops querying an orientation provider and loses `phax orient`, its config key, prompt section, phase file, grant and events

## 1. Context

A project can declare `"orient": { "command": … }` in `phax.json`, `phax.local.json` or `~/.phax/config.json`, and the nearest layer wins. When a fresh phase starts, after its setup commands, phax runs the command with `{"files": [...]}`: the phase's planned create, edit and optional files. It expects rows `{id, title, severity, trigger}` back and weaves at most 50 of them into the first prompt under `## Orientation for this phase (expand a row before touching its files)`, followed by instructions to run `phax orient <id>` and `phax orient --file <path>`. A failure is advisory: phax prints a warning and dispatches with no section. Every phase folder gets `orient-brief.json` (`ok`, `failed` or `not-configured`), written even when nothing is configured. When orient is configured, the in-phase agent may run `phax orient` without an `agentCommands` entry, and `security.json` records it with source `orient`. Three telemetry events (`orient.brief.computed`, `orient.pull.served`, `orient.pull.empty`) go to the daily journal `~/.phax/telemetry-YYYY-MM-DD.jsonl`.

When no orient provider is configured, which is every project today, a phase already runs as it will after this change. phax runs no query and builds the prompt with no section. The phase folder differs in one file only (`orient-brief.json` `not-configured`), and the grant list has no `phax orient`.

No project configures `orient`: phax, steme-lab, phax-cockpit and louloupapers were checked on 2026-10-05. `examples/hello-world/orient.mjs` is phax's own example. None of orient's shapes is a `@lbdremy/phax-schemas` format. `orient-brief.json` and `security.json` carry no `$schema`, telemetry lines carry none either, and the config is not a package format. No `$schema` URL served by docs.phax.run changes, so the site's deploy guard is not involved. The site pages that mention orient are rebuilt from the README and the CLI reference at the next release.

On 2026-10-06 the author reordered NEXT_STEPS §Before steme's audit so that the removals come first: `drop-orient`, then `drop-gate-scopes`, then `gate-request` and the brief. Since then, `brief-replaces-orient`, `drop-gate-scopes` and `gate-request` have been abandoned and archived, and each is being re-briefed (`docs/briefs/brief-provider.md`, `drop-gate-scopes.md`, `gate-request.md`). All three re-briefs assume this spec has landed.

## 2. Problem

orient is surface that nobody uses and that is about to freeze. The CLI and config contract freeze for 1.0 (NEXT_STEPS §Road to 1.0.0), and orient is still in it: a config key in three layers, a command with its long help and usage entry, a prompt section, a file in every phase folder (written even when nothing is configured), an agent-command grant source and three telemetry events. The 1.0 announcement draft presents it as a shipped feature.

Its contract is also the wrong one. It answers with the rule in general, never with the state of the code, and it sees only file names (abandoned `brief-replaces-orient` §2). The replacement is designed again from the agent's need as spec `brief-provider`. Building that next to a live orient would mean either designing the new channel beside the old one or having its plan carry a retirement too. Every spec in the queue (`drop-gate-scopes`, `gate-request`, `brief-provider`) is now being re-briefed on the assumption that orient is gone first.

## 3. Product goal

phax stops querying an orientation provider at phase start, stops weaving an orientation section into the first prompt, stops writing `orient-brief.json`, and loses `phax orient`, the `orient` config key, the `orient` grant source and the orient telemetry events. Every phase of every project then runs exactly as a phase runs today when no orient provider is configured, apart from the one file and the one grant that existed only for orient. Nothing replaces it in this change, and nothing eases its removal. The README, CLI reference, usage spec, config schemas, example and announcement draft stop describing it. History is kept as written: archived artifacts, authoring briefs, earlier records and the git history.

> After this change, every phase runs as a phase with no orient provider runs today, and nothing outside kept history remembers that orient existed.

## 4. Terminology

- **Orientation provider** — The removed extension point: the `orient` config key, its `{files}` and `{expand}` requests and its row answers. It is named in this spec only to say what is removed.
- **Phase start** — What phax does for a phase between creating its folder and the agent's first turn: branch and worktree creation, setup commands, prompt building, model resolution and security posture. A fresh start (`phax run`, or `phax resume` after `phax reset-phase`) builds a prompt. A resumed session does not.
- **No-provider baseline** — What the current release does for a project that declares no orientation provider: the prompt it builds, the commands it runs and the files it writes. This change keeps every phase on that baseline, except for the orientation brief file it writes today in every case.
- **Agent-command grant** — A command the in-phase agent may run, frozen into the phase's `security.json` `agentCommands` with a `source`, which says where the grant came from.
- **Kept history** — Tracked text that records what was decided or found at a date and is changed only by its own revision, if at all: everything under `docs/specs/` and `docs/plans/` (archived artifacts, live specs and plans with their sidecars and approval records), authoring briefs under `docs/briefs/`, dated findings under `docs/spikes/`, and `NEXT_STEPS.md`, the author's queue (except its cross-run item, §5 r-docs). Untracked: the git history, records on `phax/records/v1`, phase folders of earlier runs and telemetry journals.
- **Live tree** — Every tracked file that is not kept history: code, tests, scripts, packages, generated contract files, the README, `docs/` outside the kept paths, examples and the shipped skills.

## 5. Functional requirements

### 5.1 No query at phase start

WHEN a phase starts THE system SHALL start no process for the phase between the end of its setup commands and the launch of its agent.

### 5.2 The first prompt is the no-provider prompt

The system shall build each phase's first prompt with exactly the sections, order and text it builds today for a project that declares no orientation provider.

### 5.3 No orientation file in the phase folder

WHEN a phase starts THE system SHALL write to the phase folder the files it writes today for a project that declares no orientation provider, except the orientation brief file, which it SHALL NOT write.

### 5.4 Resume and reset change only through the shared phase start

WHEN `phax resume` continues a phase, or re-runs one after `phax reset-phase`, THE system SHALL behave as it does today for a project that declares no orientation provider.

### 5.5 The agent's grants come from config and gate only

The system shall grant the in-phase agent exactly the commands of `security.agentCommands` and the commands of the phase's gate, whatever the project's configuration.

### 5.6 Two grant sources in security.json

The system shall write each `security.json` agent-command `source` as one of exactly two values, `config` and `gate`, and shall decode no other value.

### 5.7 No orientation key in the configuration contract

The configuration contract of `phax.json`, `phax.local.json` and `~/.phax/config.json` shall have no orientation provider key, and shall keep every other key and its layer precedence as it is today.

### 5.8 The local schemas follow the contract

WHEN `phax schema upgrade` runs THE system SHALL write a `phax.schema.json` and a `phax.user.schema.json` whose top-level properties are exactly those of the configuration contract, and SHALL leave `phax.json` unchanged.

### 5.9 No orientation command

The system shall offer no command that queries an orientation provider, and `phax --usage`, `phax --help`, `phax.usage.kdl`, `docs/cli/reference.md` and the README CLI summary shall list only the commands it offers.

### 5.10 Ten semantic telemetry events

The system shall emit and decode exactly these semantic telemetry event types: `state.transition`, `adapter.call.started`, `adapter.call.succeeded`, `adapter.call.failed`, `step.started`, `step.completed`, `gate.evaluated`, `artifact.generated`, `agent.model.resolved`, `security.policy.applied`.

### 5.11 Records read as they do today

WHEN `phax records list` or `phax records explain` reads a phase record that carries a file the current release does not write THE system SHALL read the record as it does today, without error and without interpreting that file.

### 5.12 The docs describe no orientation provider

The README, `docs/cli/reference.md`, `phax.usage.kdl`, the generated config schemas, `docs/blog/announcing-phax-1.0.md`, `examples/hello-world/`, `docs/ideas/` and the cross-run durable context item of `NEXT_STEPS.md` shall describe no orientation provider, no `phax orient`, no orientation prompt section and no orientation brief file.

### 5.13 Counts match the hooks listed

README §Extend phax shall state a hook count equal to the number of hook subsections it lists, and the 1.0 announcement draft shall state a provider count equal to the number of providers it lists.

### 5.14 The example ships a script for each hook

The hello-world example shall declare only hooks it ships a script for, and ship no script for a hook it does not declare.

### 5.15 The live tree is swept

The live tree shall contain no case-insensitive occurrence of the string `orient`.

## 7. Non-goals

- Any replacement: no feed-forward channel, `brief` key, `phax brief` or prompt section. That is spec `brief-provider` (re-briefed from the abandoned `brief-replaces-orient`).
- Dropping `scopes`, pending diagnostics or `gate-pending` (spec `drop-gate-scopes`), and the gate request (spec `gate-request`).
- Removing or changing the shared provider runner that the scope provider and the plan auditor use.
- Any message, dedicated refusal, alias, deprecation, migration, upgrade note or "removed" section for the removal. Restating or testing the ordinary unknown-key refusal (exit 2) or unknown-command error for it is also excluded.
- Reading, rewriting, moving, pruning or listing files written by earlier releases: orientation brief files in earlier phase folders and on `phax/records/v1`, earlier `security.json` grants, and earlier telemetry journal lines.
- A next shape in `@lbdremy/phax-schemas`, a `version` bump of `security.json` or `phax.json`, or a change to any served `$schema` URL.
- Editing other specs (`oracle-phases`, `phase-decision-requests`), authoring briefs, spikes or archived artifacts. §10 states the wording their own revisions must change.
- Changing anything else in the phase start, the prompt, `phax resume`, `phax reset-phase` or the fix loop. `phax run --append` (spec `headless-review`) is not built yet and inherits the phase start as it stands.
- Redeploying docs.phax.run outside a release.

## 8. Acceptance criteria

### A phase starts on the no-provider baseline

Given a three-phase run of the hello-world plan under a fake shell that records every process phax starts, with setup command `pnpm install`, and golden first prompts captured from the current release for the same plan with no orientation provider configured, when phase-01 and phase-02 start, then for each phase, the processes started from the end of `pnpm install` to the agent launch are none, and each phase's `prompt.md` equals its golden prompt byte for byte. (refs §5.1, §5.2)

### The phase folder holds the baseline files, one fewer

Given the same run and an explicit expected list of phase-folder file names: the current release's no-provider list for phase-01 at agent launch, minus its orientation brief file, when phase-01's agent is launched, then the names of the files in phase-01's folder equal the expected list, with none missing and none added. (refs §5.3)

### Resume and reset need nothing of their own

Given phase-02 of that run stopped with its gate exhausted, when `phax resume <run>` runs, then `phax reset-phase <run> phase-02` runs, then `phax resume <run>` runs again, then the first resume writes no new `prompt.md` and starts no process between setup and the agent. After the reset, phase-02 gets a fresh `prompt.md` equal to its golden prompt and a phase folder matching the expected list of ac-phase-folder. Neither resume exits differently from the no-provider baseline. (refs §5.4, §5.1, §5.2, §5.3)

### Grants come from config and gate only

Given a run in `secure` mode on a provider with a command allowlist, `security.agentCommands: ["node"]` and a gate profile whose only step is `pnpm test`, when phase-01 starts, and later is resumed, then each time, phase-01's `security.json` `agentCommands` holds exactly `{ "command": "node", "source": "config", "explicit": true, … }` and `{ "command": "pnpm test", "source": "gate", "explicit": false, … }`, and the allowlist handed to the provider holds exactly `node` and `pnpm test`. (refs §5.5, §5.6, §5.4)

### The grant source enum has two values

Given a `security.json` document that is valid in every other respect, when it is decoded with an agent-command `source` of `config`, then `gate`, then `plugin`, then the first two decode and the third is rejected. (refs §5.6)
