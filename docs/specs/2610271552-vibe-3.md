# Mistral Vibe 3

## 1. Context

Mistral Vibe 3.0.3 is a rewrite: a Rust client (`vibe-rs`) driving a Python app-server. phax drives it as `mistral-vibe` for phase, fix and handoff turns, authoring and decide writers, review turns and stop turns. Nobody uses Vibe through phax today, so this change needs no migration.

What phax does today, written against Vibe 2.x:

- It spawns `vibe -p <prompt> --agent auto-approve --output streaming --workdir <worktree> [--add-dir <root>]…`, plus `--trust` in unsafe mode, with the model chosen through `VIBE_ACTIVE_MODEL` (a `phax-mistral-medium-3.5-<effort>` alias installed by `phax agent setup mistral-vibe`).
- It reads the answer from the last stream line whose `content` is a string.
- It finds the session id by scanning `~/.vibe/logs/session/session_*/meta.json` for a directory modified since the turn started whose working directory matches.
- It reads usage from that `meta.json`'s `stats` block, and the transcript from `messages.jsonl` beside it.
- It records Vibe's security capability as filesystem jail `partial`, command enforcement `none`, and stop turns as narrowing `none`. A read-only session (`readOnly`) runs with Vibe's full tool set. Sealed completions are refused ("not yet supported for mistral-vibe").

Facts from three live probes against Vibe 3.0.3 on 2026-10-27 (model `phax-mistral-medium-3.5-off`):

- **Stream.** Each line is a typed entry (`type`: `message`, `effect`, `callback`) carrying `sessionId`. A message's `content` is an array of blocks: `{"type":"message","role":"assistant","content":[{"type":"text","text":"PONG"}],…}`.
- **Store.** Sessions live under `logs/session/unified/<session id>/` (`meta.json`, `journal/*.jsonl`, `chunks/`, format `mistral.vibe.unified-session-store/v1`). There is no `session_*` directory, no `messages.jsonl`, and `meta.json` has no `stats`. The journal is an internal recovery log, not a readable transcript.
- **Export.** `--output-dir DIR` writes `DIR/export.json` on every exit (`schema_version: 1`), with `session_id`, `usage` {`input_tokens`, `output_tokens`, `cached_input_tokens`, `total_tokens`}, `cost_usd`, `steps`, `outcome`, `exit_code` and `vibe_version`. Its usage and cost count the run only, not the earlier turns of a resumed session.
- **Enforcement.** Under `--agent accept-edits` with `VIBE_OUTSIDE_WORKDIR=deny` and `VIBE_TOOLS='{"bash":{"permission":"ask","allowlist":["git status"]}}'`:
  - `git status` ran.
  - `ls /etc`, `cat <outside file>` and `read_file <outside file>` were refused ("outside_workdir = \"deny\" forbids access").
  - Each of `git status && touch x`, `git status; touch x`, `git status | tee x`, `git status $(touch x)`, `echo hi > x`, `pwd` and a background `process.start` was refused (`tool_denied`).
  - `write_file` and `edit` inside the workdir ran.
  - `run_typescript` has no IO of its own (`Deno`, `require` and `Bun` are undefined).
  - Every refusal reached the model as a tool error and the run finished (exit 0).
- **Narrowing.** `--enabled-tools read_file --enabled-tools grep` refused `write_file` and `bash` ("denied by approval policy").
- **Auto-approve.** Vibe documents that `--auto-approve` and the `auto-approve` agent skip the outside-workdir check and the denylists.
- **Models.** Vibe 3 still reads phax's `[[models]]` alias blocks. The base model's thinking levels are `off`…`max`, with no `xhigh`.

Ground read:

- `src/infra/providers/mistralVibe.ts`: argv, spawn, session-id discovery, transcript capture.
- `src/schemas/vibeOutput.ts`: stream line schema (`content` a string), `findVibeSessionId`.
- `src/domain/records/usage.ts`, `src/schemas/runRecord.ts`: `extractVibeUsage` from `meta.json` `stats`; `VibeTokenUsage` with four tool-call counts.
- `src/domain/security/capabilities.ts`, `src/domain/security/stopPosture.ts`, `src/app/interactiveStop.ts`: `partial`/`none` capability, narrowing `none`, `turnsCanWrite` true only for Vibe.
- `src/infra/providers/dispatcher.ts`: Vibe sealed completion refused; Vibe transcript read from the store root.
- `docs/security.md`: provider capability table, shell model, what phax reads from a provider's store.
- `docs/specs/2610271510-provider-failures.md`: owns the per-provider session-outcome reader and the failure kinds; leaves the rest of Vibe 3 to this spec.

## 2. Problem

phax cannot run a single Vibe 3 session. The answer is never found because `content` is no longer a string. Even with an answer, the session id is never found because the store moved, and the usage and transcript are lost because `stats` and `messages.jsonl` are gone. All of this fails as an invocation error that names none of it.

The security posture phax documents for Vibe is also now wrong in both directions. phax runs Vibe under `auto-approve`, which turns off every control Vibe 3 offers, and so records it as `partial`/`none`. Yet Vibe 3 can now confine file and shell calls to the writable roots, allow exactly the phase's commands, and narrow a session to reading tools. Because of that recorded posture, secure-mode routing skips Vibe, its stop turns write, and it cannot serve a read-only session or a sealed completion.

## 3. Product goal

phax runs Mistral Vibe 3 sessions end to end: it reads the answer, session id, usage and transcript from what the session itself hands phax, never from Vibe's private store. In secure mode it confines Vibe as tightly as Claude Code: edits only inside the writable roots, the shell only for the phase's agent commands, reading tools only for a read-only session, no tools for a sealed completion.

> phax reads a Vibe session only from what that session hands it, and never runs Vibe in secure mode with a control turned off.

## 4. Terminology

- **Vibe export.** The `export.json` Vibe writes into the output directory phax gives a headless session, once per turn.
- **Turn stream.** The stdout lines of one headless Vibe turn, which phax already keeps in the phase or session folder.
- **Agent commands.** The phase's frozen command set (gate commands ∪ configured agent commands), as recorded in `security.json`.
- **Writable roots.** The worktree plus `security.filesystem.allowWrite`.

## 5. Functional requirements

### 5.1 Answer

WHEN a Vibe turn ends THE system SHALL take as its answer the text blocks of the last assistant message entry of the turn stream, joined in order.

### 5.2 Session id

WHEN a Vibe turn ends THE system SHALL take the session id from the turn's Vibe export.

### 5.3 Usage

The system shall record a Vibe session's usage as the sum over its turns' Vibe exports of input tokens, cached input tokens, output tokens and cost.

### 5.4 Transcript

The system shall use the turn streams of a Vibe session, in turn order, as that session's transcript.

### 5.4b No stream, no transcript

IF a recorded Vibe session has no turn stream phax kept (a session the person ran in Vibe's TUI) THEN the system SHALL record its transcript as missing, `not-found`.

### 5.5 No store reads

The system shall not read Vibe's home directory to find a session, its usage or its transcript.

### 5.6 Version floor

IF the installed Vibe is older than 3.0.3 THEN the system SHALL refuse to start a Vibe session with a message naming the installed version and 3.0.3.

### 5.7 Secure edits

WHILE a Vibe session runs in secure mode THE system SHALL let it edit files inside the writable roots without approval and refuse every tool call no rule allows.

### 5.8 Secure filesystem jail

WHILE a Vibe session runs in secure mode THE system SHALL refuse its file and shell calls that reach outside the writable roots.

### 5.9 Secure shell

WHILE a Vibe session runs in secure mode THE system SHALL run a shell command, foreground or background, only when it matches one of the agent commands.

### 5.10 No auto-approve in secure mode

WHILE a Vibe session runs in secure mode THE system SHALL NOT run it with Vibe's auto-approve agent or flag.

### 5.11 User configuration untouched

The system shall apply 5.7–5.9 per invocation, without writing the user's Vibe configuration files.

### 5.11b User configuration cannot widen secure mode

IF the user's Vibe configuration allows more than 5.7–5.9 (a tool's path or command allowlist, `bypass_tool_permissions`) THEN the system SHALL still confine the secure session as 5.7–5.9 state.

### 5.12 Recorded capability

The system shall record Vibe's command enforcement as `prefix` and its filesystem jail as `strong`.

### 5.13 Read-only sessions

WHEN a session is read-only THE system SHALL run Vibe with only its reading tools, plus the shell for exactly the agent commands it is granted.

### 5.14 Stop turns

The system shall run Vibe's first and closing stop turns read-only and record their narrowing as `read-only-tools`.

### 5.15 Sealed completion

WHEN a sealed completion is routed to Vibe THE system SHALL run it with no tools enabled.

### 5.16 Unsafe mode

WHILE a Vibe session runs in unsafe mode THE system SHALL run it with Vibe's auto-approve agent and `--trust`, as today.

## 6. Surface

### internal: Vibe argv, secure-mode phase turn (indicative)

before:

    VIBE_ACTIVE_MODEL=phax-mistral-medium-3.5-medium \
    vibe -p <prompt> --agent auto-approve --output streaming --workdir <worktree> --add-dir ~/.phax

after:

    VIBE_ACTIVE_MODEL=phax-mistral-medium-3.5-medium \
    VIBE_OUTSIDE_WORKDIR=deny \
    VIBE_TOOLS='{"bash":{"permission":"ask","allowlist":["pnpm typecheck","pnpm test"]}}' \
    vibe -p <prompt> --agent accept-edits --output streaming --workdir <worktree> --add-dir ~/.phax \
         --output-dir <phase folder>/vibe-export/<turn>

A read-only session adds `--enabled-tools read_file --enabled-tools grep`, plus the shell for its agent commands when it has any. A sealed completion enables no tool.

               "toolCallsAgreed": 4, "toolCallsRejected": 0, "toolCallsFailed": 1, "toolCallsSucceeded": 3 }

## 7. Non-goals

- Classifying a Vibe session's failure (exit codes 1–4, `outcome`, failure kinds): the `provider-failures` spec owns the session-outcome reader. This spec only establishes that the Vibe export is reliable on 3.0.3, which is the condition `provider-failures` set for reading it.
- `--agent-socket` / `vibe run-server`: experimental and hidden in 3.0.3. It is an input to the `isolated`-mode spike, not to secure mode.
- Interactive resume of a Vibe session (`vibe --resume <id>` in the TUI): it stays unsupported, since it cannot be verified headless.
- Network control: Vibe has none to apply, so the `network` column stays `None`.
- MCP scoping for Vibe sessions, beyond what read-only narrowing and sealed completions already drop.
- Vibe's limits (`--max-turns`, `--max-price`, `--time-limit`) and `--prompt-file`.
- An `xhigh` alias: the base model offers no such thinking level.
- Reading Vibe 2.x sessions, or any back-compat for Vibe usage recorded before 0.29.0 beyond the versioned readers that already exist.

## 8. Acceptance criteria

### The answer is read from a Vibe 3 stream

Given a turn stream whose last assistant message entry has content `[{"type":"text","text":"PONG"}]`, when the turn ends, then the answer is `PONG`. (refs §5.1)

### Session id and usage come from the exports

Given a session of two turns whose Vibe exports carry `session_id` `b8e0…` and usage 10987/3200/3 then 34588/9600/288 with costs 0.016503 and 0.054042, when the session is recorded, then its session id is `b8e0…` and its usage is `inputTokens` 45575, `cachedInputTokens` 12800, `outputTokens` 291 and `costUsd` 0.070545. (refs §5.2, §5.3)

### The transcript is the kept streams

Given a session whose phase turn and fix turn each kept a turn stream, when its transcript is captured, then the transcript is the two streams in turn order. (refs §5.4)

### A person's Vibe session has no transcript

Given a closed stop that recorded a Vibe session phax never ran headless, when its transcripts are captured, then that session's transcript is `missing` with reason `not-found`, and the close is not refused. (refs §5.4b)

### Nothing is read from Vibe's home

Given `VIBE_HOME` pointing at an unreadable directory, when a Vibe session runs and is recorded, then the answer, session id, usage and transcript are all found. (refs §5.5)

### An old Vibe is refused

Given an installed Vibe reporting `2.13.0`, when phax starts a Vibe session, then it refuses before spawning the session and names 2.13.0 and 3.0.3. (refs §5.6)

### A secure session is confined

Given a secure Vibe phase whose agent commands are `git status`, when the agent writes a file in the worktree, runs `git status`, then `git status && touch x`, `ls /etc`, and a background `touch y`, then the file is written, `git status` runs, the other three are refused, neither `x` nor `y` exists, and the turn finishes. (refs §5.7, §5.8, §5.9)

### Secure mode never auto-approves and never writes the user's config

Given a secure Vibe phase, when phax spawns it, then its argv carries neither `--agent auto-approve` nor `--auto-approve`, and the user's `config.toml` is byte-identical afterward. (refs §5.10, §5.11)

### A loose user config does not widen secure mode

Given a `VIBE_HOME` whose `config.toml` sets `bypass_tool_permissions = true`, `[tools.bash] allowlist = ["touch"]` and `[tools.read_file] allowlist` naming a directory outside the worktree, when a secure Vibe phase whose agent commands are `git status` tries `touch x` and reads a file in that directory, then both are refused. (refs §5.11b)

### Vibe satisfies strict secure routing

Given secure mode and `providerPriority` `["mistral-vibe", "claude-code"]`, when a phase is routed, then it routes to `mistral-vibe`, and its `security.json` has `downgraded: false` and no `partial-filesystem` mark. (refs §5.12)

### A read-only session cannot write

Given a read-only Vibe session with no agent commands, when the agent tries `write_file` and `bash touch x`, then both are refused and `x` does not exist. (refs §5.13)

### Stop turns are read-only

Given a Vibe phase stopped and closed, when its `security.json` is written, then each first and closing turn reads `"narrowing": "read-only-tools"`, and the worktree is unchanged by those turns. (refs §5.14)

### A sealed completion runs on Vibe

Given a sealed completion routed to `mistral-vibe`, when it runs, then it returns the model's answer and its argv enables no tool. (refs §5.15)

### Unsafe mode is unchanged

Given an unsafe Vibe phase, when phax spawns it, then its argv carries `--agent auto-approve` and `--trust`. (refs §5.16)

## 9b. Arbitrated questions

### q-jail — Does secure Vibe record a `strong` filesystem jail, satisfying strict secure routing?

- strong — Record `strong` with command enforcement `prefix`, like Claude Code — abandons: Telling tool-level enforcement from an OS sandbox in the record. Vibe's shell path check is static, so code an allowed agent command runs (a test script) can still read outside, exactly as under Claude Code's allowlist.
- partial — Keep `partial` and the `partial-filesystem` mark — abandons: Ever routing Vibe in secure mode, the default, except as the terminal fallback. The hardening would ship and routing would keep ignoring it.

Recommendation: strong — The probes show Vibe 3 refuses the same calls Claude Code's secure flags refuse, compound commands and background processes included. `strong` already means tool-level confinement for Claude Code, so recording Vibe as `partial` would only keep a provider out of secure routing on a difference the record does not otherwise draw.

Decision: strong — by operator (Rémy Loubradou), 2026-10-27
Why: The probes show Vibe 3 refuses the same calls Claude Code's secure flags refuse, compound commands and background processes included. `strong` already means tool-level confinement for Claude Code, so recording Vibe as `partial` would only keep a provider out of secure routing on a difference the record does not otherwise draw.

### q-tool-calls — What becomes of the four Vibe tool-call counts in recorded usage?

- drop — Drop `toolCallsAgreed/Rejected/Failed/Succeeded`; Vibe usage is tokens and cost, like Claude Code's and Codex's — abandons: The only per-session tool approval counts phax recorded for any provider. No command displays them today.
- derive — Count them from the turn streams' `effect` entries (`decision`, `status`) — abandons: Reading the stream's tool entries, which are unversioned (unlike the export's `schema_version`), so phax would own an accounting Vibe never documented and that breaks silently when the entries change.

Recommendation: drop — Nothing reads the counts. The export, which carries a schema version, has no such field, and phax prefers recording what the provider states over reconstructing it.

Decision: drop — by operator (Rémy Loubradou), 2026-10-27
Why: Nothing reads the counts. The export, which carries a schema version, has no such field, and phax prefers recording what the provider states over reconstructing it.

## 10. Implementation-planning note

Settled:

- Each headless Vibe turn gets its own output directory under the phase or session folder. Its Vibe export is the source of the session id, usage and cost. The turn stream is the source of the answer and the transcript.
- The store-root reads for Vibe go away: session discovery by mtime and working directory, `meta.json` usage, and the `messages.jsonl` transcript.
- Secure mode passes its controls as `VIBE_*` environment variables (`VIBE_OUTSIDE_WORKDIR`, `VIBE_TOOLS`) with `--agent accept-edits`. The agent commands become `[tools.bash].allowlist`. Vibe merges layers deeply (environment over user TOML, a list replacing a list, unset keys kept from below), so secure mode also sets every key that could widen it: `bypass_tool_permissions = false`, and an empty `allowlist` on each file tool. The probes confirmed that Vibe denies a non-allowlisted call headless (`tool_denied`) and that the run goes on.
- Read-only uses `--enabled-tools` (reading tools, plus `bash` with the agent commands' allowlist when granted). Vibe's stop turns no longer write, so restoring a writing closing turn's edits loses its only provider.
- Vibe usage at `$schema` 0.29.0, with no back-compat shim: required fields only; older stamps go through the existing versioned readers.
- Vibe 3.0.3 is the target and the floor.

Left open:

- How the installed version is read (`vibe --version` once per process or per session) and where the refusal surfaces.
- The exact reading-tool set for read-only (`read_file`, `grep`, and whether `skill` belongs), and how a sealed completion disables every tool (an `--enabled-tools` matching nothing, or `--disabled-tools`).
- Whether `VIBE_TOOLS` should also deny `web_fetch`/`web_search` in secure mode. Recommend no, matching Claude Code's secure flags.

Constraints:

- Every change must hold on Vibe 3.0.3: e2e tests run against the real CLI deliberately (`pnpm test:e2e:real`), and unit fixtures use the probe streams and exports.
- `provider-failures` also edits the Vibe adapter. Its Vibe session-outcome reader must read the Vibe export and the V3 stream shape this spec establishes, so plan this spec's reading phases first or fold the two Vibe readers into one.
- Never write `~/.vibe/config.toml` except through `phax agent setup mistral-vibe`, which is unchanged.
