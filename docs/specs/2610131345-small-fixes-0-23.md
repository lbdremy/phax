# Small fixes for 0.23: Gate-Log names the passing attempt, headless authoring retries once, served schemas stop misreading stamps

## 1. Context

Three small, separate defects from NEXT_STEPS "Small follow-ups". The author decided on 2026-10-13 to ship them under one spec and one short plan. None depends on another, and the `standard` gate checks each one.

Gate-Log trailer. Every phase commit ends with a trailer block that includes `Gate-Log: <path>`. Since gate-attempt-records, a phase's gate attempts are numbered once across every entry into its gate. The attempt that passes can be 03, or 07 after a resume. The fix loop already returns the passing attempt's log path. The run ignores it and always writes `checks-attempt-01.log`. A run that resumes a phase left `passed` (for example after a pre-commit hook rejected the commit) commits without running the gate again. Nothing in phax reads the trailer. It exists for a person reading `git log`.

Headless authoring. `phax artifact new spec|plan --headless` runs one session and decodes its final message as the spec or plan document. If the message is not JSON, or the decoder refuses it, phax writes nothing and fails. When the message is not JSON, today's refusal quotes its first 200 characters and does not name the parser error. The session folder holds `brief.md`, `prompt.md`, `output.jsonl` and, once a document is accepted, `document.json`. The authoring record carries those files, and its manifest says nothing about a retry.

Served schemas. Each persisted format's JSON Schema describes `$schema` as "The <format> format and the phax release that wrote this file". That text is in every released snapshot under `packages/schemas/snapshots/`, in the package's `json/`, and on docs.phax.run, which serves each release-named snapshot byte for byte. Since open-next-release, a stamp names the release that last changed the format's shape, as the README and `docs/release.md` say. The snapshot check compares the generated schema with the latest released snapshot, annotations included. Any change to the wording therefore counts as a new shape for every format.

Ground read:

- `src/app/executePlan.ts` — The phase commit call passes `join(phaseFolderPath, "checks-attempt-01.log")` as `gateLogPath` whichever attempt passed, and discards the `GateOutcome` the fix loop returns; a phase resumed from `passed` (resume-from-commit) commits without running its gate.
- `src/app/commit.ts` — `buildCommitBody` writes the fixed trailer block, ending `Gate-Log: <gateLogPath>`.
- `src/app/fixLoop.ts` — Numbers each attempt with `nextAttemptNumber` over the phase folder and, on a pass, returns `GateOutcome { attemptLogPath }`, the passing attempt's log.
- `src/app/gates.ts` — Every attempt that passes writes its log, even with no steps, so a passed phase always has a recorded attempt.
- `src/domain/gate/attemptFiles.ts` — Attempts are numbered once across every entry into a phase's gate; `lastRecordedAttempt` names the highest attempt with a log.
- `src/app/authorArtifact.ts` — `parseAuthoredDocument` refuses a final message that is not JSON (the reason quotes its first 200 characters, not the parser error) or that the document decoder refuses (first violation); the session then fails with nothing written.
- `src/domain/authoring/jsonText.ts` — Strips one code fence or picks the last balanced top-level object before parsing.
- `src/domain/authoring/prompt.ts` — Builds the one authoring prompt (skill, JSON Schema, brief); there is no follow-up prompt today.
- `src/ports/backend.ts` — `resumeAgentSession(sessionId, prompt, options)` resumes a session, as the fix loop and handoff generation already do.
- `src/infra/providers/claudeCode.ts` — Each call opens its transcript with flag `w`, so a resume onto the same `output.jsonl` would overwrite the first answer's transcript.
- `src/app/writeAuthoringRecord.ts` — The record carries only `brief.md`, `prompt.md`, `document.json` and `output.jsonl`; usage is read from `output.jsonl`.
- `src/schemas/authoringRecord.ts` — The manifest has no retry field and its doc comment says a headless session is never resumed.
- `src/schemas/schemaUrl.ts` — `schemaUrlField` describes `$schema` as "the phax release that wrote this file".
- `packages/schemas/build/snapshots.ts` — The snapshot check compares the generated schema with the latest released snapshot as parsed JSON (`isDeepStrictEqual`), annotations included, and never rewrites a released snapshot.
- `tests/unit/schemasPackage/snapshots.test.ts` — Pins the snapshot gate's findings and `--write` plan.
- `site/build/schemas.ts` — docs.phax.run serves each release-named snapshot byte for byte at /schemas/<format id>/<release>.json, and each frozen copy under site/retired-schemas/.
- `docs/release.md` — A stamp names a format's shape: the release that last changed the format, or the opened version while it has a `next` snapshot.
- `README.md` — `$schema` names the release that last changed the format; each URL stays up for good; pre-1.0 readers refuse a report stamped in an older shape.
- `NEXT_STEPS.md` — Small follow-ups: the Gate-Log entry, the served-schemas wording entry, and the headless-authoring malformed-JSON entry (2026-10-06, 2026-10-08).

## 2. Problem

Gate-Log trailer: on any phase whose gate failed at least once, or that was entered more than once, the trailer names the wrong log. A reader who follows it sees attempt 01, which may be a failing attempt, and not the one that let the commit through.

Headless authoring: one stray character, or one missing key in an otherwise good document, throws away a whole session (several minutes, ~23 KB of output). This happened on 2026-10-06 (a stray code expression at character 22 700) and on 2026-10-08 (valid JSON missing `acceptanceCriteria[0].refs`). Both reruns succeeded, so the session could have fixed its own answer if told what was wrong. When the message is not JSON, the refusal does not say where parsing failed, which leaves neither the operator nor a retry anything to act on.

Served schemas: the served text contradicts the README and the release doc on what a stamp means. Rewording it today would put a `next` snapshot on every format and move every stamp at once. Before 1.0, readers refuse a report or answer stamped in an older shape. Every gate step and brief provider stamping `gate-report`/`brief-report` at its current shape would therefore be refused, all for a sentence no decoder reads. That is the forced upgrade open-next-release removed.

## 3. Product goal

Each phase commit's `Gate-Log` names the log of the attempt that let it through. A headless authoring session whose document is refused gets one chance, in the same session, to fix it, and nothing about the first answer is lost. The served schemas say what a stamp means, and no stamp moves because the wording changed.

> A fix tells the truth about what happened, and it does not force anyone else to upgrade.

## 4. Terminology

- **attempt** — One run of a phase's gate steps, numbered NN in `checks-attempt-NN.log`. Numbering continues across every entry into the phase's gate.
- **entry** — One pass of a run into a phase's gate: the first execution, or a resume that runs the gate again.
- **passing attempt** — The attempt whose gate passed, after which the phase was marked passed. No further attempt of that phase runs after it.
- **recorded attempt** — An attempt whose `checks-attempt-NN.log` exists in the phase folder.
- **refused document** — A headless authoring session's final message that phax does not accept as the requested document: either it is not JSON, or the spec or plan document decoder refuses it (schema or traceability check). Provider errors, rate limits, usage limits, security enforcement failures and commit failures are not refused documents.
- **refusal** — The one-line reason a document was refused: the JSON parser's error and where it failed, or the decoder's first violation.
- **retry** — The one resume of a headless authoring session, made after its first final message was refused, asking for the whole document again.
- **annotation keywords** — Exactly the JSON Schema keywords `description`, `title` and `examples`, wherever they appear as keywords of a (sub)schema. A property that happens to be named `description`, `title` or `examples` is not an annotation keyword.
- **shape** — What a format's schema accepts. The release that last changed a format's shape is what its `$schema` stamp names.
- **released snapshot** — A release-named snapshot `packages/schemas/snapshots/<format>/<X.Y.Z>.schema.json`, served byte for byte at `https://docs.phax.run/schemas/<format>/<X.Y.Z>.json`.

## 5. Functional requirements

### 5.1 Gate-Log names the passing attempt

WHEN a phase's gate passes during the current entry THE system SHALL name, in that phase commit's `Gate-Log` trailer, the log of the attempt whose gate passed.

### 5.2 Gate-Log on a commit-only resume

WHEN a run resumes a phase left passed and commits it without running its gate THE system SHALL name, in the `Gate-Log` trailer, the log of the highest-numbered recorded attempt in the phase folder.

### 5.3 Gate-Log never names a missing log

IF the phase folder holds no recorded attempt when the phase is committed THEN the system SHALL write the trailer as `Gate-Log: none` and commit the phase without pausing the run.

### 5.4 One retry on a refused document

WHEN a headless authoring session's final message is a refused document THE system SHALL resume that same session once, with a retry prompt that states the refusal and asks for the whole document again as the final message.

### 5.5 A not-JSON refusal names the parser error

WHEN a final message is refused because it is not JSON THE system SHALL state, in the refusal, the JSON parser's error and the position where parsing failed.

### 5.6 The operator sees the retry

WHEN the system resumes a session to retry THE system SHALL print a warning naming the first refusal before the retry runs.

### 5.7 An accepted retry lands like a first answer

WHEN the retry's final message decodes THE system SHALL render, write and commit the artifact and its sidecar exactly as it does for a first answer that decodes.

### 5.8 At most one retry

IF the retry's final message is a refused document as well THEN the system SHALL fail the authoring without another retry, writing nothing to the repository and naming both refusals in its error.

### 5.9 Only refused documents are retried

IF a headless authoring session, or its retry, ends in a provider error, a rate limit, a usage limit, a security enforcement failure or a commit failure THEN the system SHALL fail with that error, as it does today, without retrying.

### 5.10 The first answer is kept

WHEN the system retries a session THE system SHALL leave the first answer's transcript in the session folder unchanged, and write the retry prompt and the retry's transcript there as separate files.

### 5.11 The record says whether a retry ran

The system shall write in every authoring record manifest a required `retry` field whose value is `none` when the session was not resumed and `retried` when it was.

### 5.12 The record carries the retry

WHEN a retried session's authoring record is written THE system SHALL include the retry prompt and the retry's transcript beside the first answer's transcript, under the same `records.transcript` policy.

### 5.13 Usage counts both turns

WHEN a retried session's authoring record is written THE system SHALL count the tokens of both the first answer and the retry in the record's usage.

### 5.14 `$schema` says what a stamp names

The system shall describe every format's `$schema` field, in the JSON Schemas it generates, as naming the release that last changed the format's shape, and never as the release that wrote the file.

### 5.15 Annotation-only change is not a new shape

WHEN the snapshot check compares a format's generated schema with its latest released snapshot, or a `next` snapshot with that released snapshot, THE system SHALL ignore the annotation keywords.

### 5.16 A real shape change is still caught

IF a generated schema differs from its latest released snapshot in anything other than annotation keywords THEN the snapshot check SHALL report it, and `--write` SHALL record a `next` snapshot, as it does today.

### 5.17 An unreleased `next` tracks the wording

WHILE a format has a `next` snapshot THE snapshot check SHALL hold that snapshot equal to the generated schema with annotation keywords included.

### 5.18 Frozen and published bytes stay put

The system shall leave every released snapshot, every frozen copy under `site/retired-schemas/` and every frozen module under `src/schemas/history/` byte for byte unchanged by this rewording.

## 7. Non-goals

- Retrying any session other than headless spec/plan authoring: phase sessions, plan extraction, review, brief and compliance sessions keep their current behavior.
- Having the provider enforce the output schema (for example, Claude Code structured output).
- More than one retry, or a configurable retry count.
- Retrying on a provider error, rate limit, usage limit, security enforcement failure or commit failure.
- Having anything in phax read the `Gate-Log` trailer, or rewriting the trailers of commits already made.
- Changing any released snapshot, any copy under `site/retired-schemas/`, or any module under `src/schemas/history/`; their old wording stays.
- Ignoring annotations anywhere other than the snapshot comparison. Decoders, served bytes and the package's generated files are unaffected.
- Treating keywords other than `description`, `title` and `examples` as annotations (for example `default`, `deprecated`, `$comment`).
- Any other NEXT_STEPS follow-up.

## 8. Acceptance criteria

### Trailer names the third attempt

Given a phase whose gate fails on attempts 01 and 02 and passes on attempt 03 within one entry, when the run commits the phase, then the commit's trailer reads `Gate-Log: <phase folder>/checks-attempt-03.log`, and no trailer names `checks-attempt-01.log`. (refs §5.1)

### Numbering across entries

Given a phase folder already holding `checks-attempt-01.log` through `checks-attempt-06.log` from an earlier entry, and a resume that runs the gate, which passes on its first attempt, when the run commits the phase, then the trailer names `checks-attempt-07.log`. (refs §5.1)

### Commit-only resume

Given a phase left passed after a pre-commit hook rejected its commit, with `checks-attempt-01.log` and `checks-attempt-02.log` recorded (02 passed), when the run resumes and commits the phase without running its gate, then the trailer names `checks-attempt-02.log` and no new attempt file appears in the phase folder. (refs §5.2)

### No recorded attempt

Given a phase left passed whose folder holds no `checks-attempt-NN.log`, when the run resumes and commits the phase, then the commit carries `Gate-Log: none`, the commit is created, and the run does not pause. (refs §5.3)

### A schema refusal is fixed by the retry

Given a fake backend whose first final message is valid JSON missing `acceptanceCriteria[0].refs` and whose resumed answer is a valid spec document, when `phax artifact new spec widget-export --headless --brief brief.md` runs, then the backend is resumed exactly once on the first session's id with a prompt containing `acceptanceCriteria[0].refs: is missing`, a warning naming that refusal is printed before the resume, and the spec and its sidecar are committed as for a first-answer success. (refs §5.4, §5.6, §5.7)

### A not-JSON refusal names the parser error

Given a fake backend whose first final message is a document with a stray `.replace("a","b")` expression inside it, and whose retry answer is valid, when the headless authoring runs, then the retry prompt and the printed warning both contain the JSON parser's error with the position where parsing failed, and the artifact is committed. (refs §5.5, §5.4, §5.7)

### Two refusals fail, naming both

Given a fake backend whose first and resumed final messages are both refused, for different reasons, when the headless authoring runs, then the command fails with today's exit code, its error names the first refusal and the retry's refusal, the backend was resumed exactly once, no artifact, sidecar or commit lands in the repository, and the authoring record's outcome is `failed` with `retry: "retried"`. (refs §5.8, §5.11)

### Limits and provider errors are not retried

Given a fake backend whose first run fails with a rate limit, or a usage limit, or an agent invocation error, or whose run succeeds but whose artifact commit fails, when the headless authoring runs, then it fails with that same error, the backend is never resumed, and the record carries `retry: "none"`. (refs §5.9, §5.11)

### A limit during the retry is not retried again

Given a fake backend whose first final message is refused and whose resume fails with a rate limit, when the headless authoring runs, then it fails with the rate limit error, no second resume is made, and the record carries `retry: "retried"`. (refs §5.9, §5.8)

### The first answer's transcript survives

Given a retried session, when the session ends, committed or failed, then the session folder's first transcript holds exactly the first run's lines, and the retry prompt and the retry's transcript are separate files beside it. (refs §5.10)

### The record carries the retry

Given a retried, committed session with `records.transcript` set to keep transcripts, and a first-answer session, when each session's authoring record is written, then the retried record's tree holds the retry prompt and the retry's transcript, its manifest carries `retry: "retried"` and usage that sums both turns' tokens, and the other record's manifest carries `retry: "none"`. (refs §5.11, §5.12, §5.13)

### `retry` is required

Given an authoring record manifest stamped at the current authoring-record-manifest shape with no `retry` key, or with `retry: "maybe"`, when phax decodes it, then it is refused, naming `retry`. (refs §5.11)

### Generated schemas say what a stamp names

Given the JSON Schemas the package generates for every format in `FORMAT_IDS`, when their `$schema` property descriptions are read, then each states that the stamp names the release that last changed the format's shape, and none contains "the phax release that wrote this file". (refs §5.14)

### The rewording records no `next`

Given the committed tree after the rewording, with released snapshots holding the old wording, when `pnpm exec tsx scripts/schemas-check.ts` runs and `--write` is planned, then the check reports no finding, `--write` plans no write and no removal for a format that differs only in annotation keywords, and every format's current stamp is unchanged apart from authoring-record-manifest, whose shape changes under rt-record-field. (refs §5.15, §5.18)

### A real change is still caught

Given a toy format whose released snapshot differs from the generated schema in a `type`, or in a property literally named `description` being added, when the snapshot check runs, then it reports today's finding and `--write` plans a `next` snapshot. (refs §5.16)

### A `next` follows the wording

Given a toy format with a `next` snapshot that differs from the generated schema only in a `description`, when the snapshot check runs, then it reports the stale `next` and `--write` rewrites it to the generated schema; and a `next` that differs from the latest released snapshot only in annotation keywords is reported as equal to it and planned for removal. (refs §5.17, §5.15)

### Published bytes do not move

Given the tree before and after the change, when every file under `packages/schemas/snapshots/` with a release name, `site/retired-schemas/` and `src/schemas/history/` is compared, then each is byte for byte identical. (refs §5.18)

## 9. Open questions for implementation planning

### Q1 — Is a change made only to annotation keywords a new shape, given that rewording `$schema`'s description touches every format? (Decided by the author on 2026-10-13; not reopened.)

- The snapshot comparison ignores `description`, `title` and `examples`. The new wording ships in the package's json/ and in each format's next `next` snapshot, and existing stamps do not move. — abandons: Byte agreement between what docs.phax.run serves at an existing stamp and what phax generates for it: each existing URL keeps the contradictory text until that format's shape next changes.
- Treat the rewording as a new shape. Every format records a `next` and every stamp moves to the opened version. — abandons: Every gate step and brief provider that stamps `gate-report`/`brief-report` at its current shape: pre-1.0 readers refuse older shapes by name, so they are all broken at once by a sentence no decoder reads. This is the forced upgrade open-next-release removed.
- Rewrite the released snapshots in place so the served URLs carry the new text. — abandons: URL immutability. A published URL starts serving different bytes, which breaks the README's "each URL … stays up for good" and the snapshot gate's rule that it never writes a released snapshot.
- Leave the wording as it is until a release that changes most formats anyway (the Effect 4 migration gives every format a `next`). — abandons: The fix itself. The contradiction keeps shipping in the package and on the site until an unscheduled migration, and this spec delivers two of its three fixes.

Recommendation: The snapshot comparison ignores `description`, `title` and `examples`. The new wording ships in the package's json/ and in each format's next `next` snapshot, and existing stamps do not move. — Decided by the author on 2026-10-13, as recommended. Only `blind` keeps both published URLs and every provider's stamps unchanged. What it gives up is temporary text on pages whose stamps phax's own docs already explain correctly. Each format's next real shape change carries the new wording, and the Effect 4 migration gives every format one. `move-all` breaks third-party report writers for no change in what is accepted. `rewrite-released` breaks a promise made in the README. `defer` ships nothing. Under every option, frozen copies under `site/retired-schemas/` and `src/schemas/history/` keep their old wording.

### Q2 — What does the retry prompt carry besides the refusal? (Decided by the author on 2026-10-13; not reopened.)

- The refusal, a statement that nothing was written, and the instruction to return the whole document again as JSON only. The schema and the brief are not repeated, because the resumed session already holds them. — abandons: Recovery when a provider compacted or truncated the resumed context and lost the schema.
- The refusal and instruction, plus the full document JSON Schema again. — abandons: A short retry. Every retry re-sends a schema of tens of kilobytes that the session already has, which inflates the cost of the very turn meant to be cheap.

Recommendation: The refusal, a statement that nothing was written, and the instruction to return the whole document again as JSON only. The schema and the brief are not repeated, because the resumed session already holds them. — Decided by the author on 2026-10-13, as recommended. Both failures seen so far were local slips in a session that still held its context, and both reruns succeeded. The refusal names the exact violation. If a provider has lost the schema, the retry is refused too and the authoring fails as it does today, naming both refusals, so nothing is worse than now.

### Q3 — What does the trailer say when a phase is committed with no recorded attempt in its folder? (Decided by the author on 2026-10-13; not reopened.)

- Write `Gate-Log: none`. — abandons: A `Gate-Log` value that is always a file path.
- Leave the trailer out. — abandons: A fixed trailer set on every phase commit. A reader cannot tell a missing trailer from a commit made by an older phax.
- Pause the run instead of committing. — abandons: Autonomy: a run stops and waits on a person over a trailer nothing reads.

Recommendation: Write `Gate-Log: none`. — Decided by the author on 2026-10-13, as recommended. Every passing attempt writes its log, so this case only arises when a folder was tampered with. An explicit literal is honest about it, keeps the trailer set fixed, and keeps the run going.

## 10. Implementation-planning note

Settled:

- The three fixes are independent. Each can be its own phase, and each is checked by the `standard` gate.
- Gate-Log: the passing attempt's log during the current entry; the highest recorded attempt on a commit-only resume; `none` if no attempt is recorded.
- Retry: exactly one, in the same session, only for a refused document (not JSON, or refused by the spec/plan document decoder). Any other failure, on the first run or on the retry, fails as today.
- The first answer's transcript is never overwritten. The retry prompt and the retry's transcript are separate files, and the record carries them.
- The authoring record manifest gains a required `retry` field with exactly the values `none` and `retried`.
- Annotation keywords are exactly `description`, `title` and `examples`.
- Released snapshots, `site/retired-schemas/` and `src/schemas/history/` are not touched.

Left open:

- The exact retry prompt wording, warning wording, and the two retry file names in the session folder (indicative in §6).
- How usage from the two turns is summed for each provider (Claude Code and Codex transcripts, Vibe session meta).
- The exact new description text, within the claim fixed by sd-wording.

Constraints:

- Respect the layers: building the retry prompt and stating refusals are pure domain logic; resuming goes through the Backend port's `resumeAgentSession`; the CLI only renders.
