### GitHub Spec Kit

- **What it is.** An MIT-licensed open-source toolkit owned by GitHub: a Python CLI (`specify`, installed with `uv tool install specify-cli`) that scaffolds skills/commands into a coding agent, plus extensions, presets, bundles, catalogs and a workflow engine (E-SDD-01, E-SDD-02). The repository history begins 2025-08-21; `v1.0.0` was published 2026-08-21 and the latest release read was `v1.4.4` of 2026-11-23 (E-SDD-01, E-SDD-05). It is free; the model cost is whatever the chosen agent costs (E-SDD-02).
- **Adoption.** 151,322 stars and 13,600 forks on 2026-11-25 (E-SDD-01); 165,212 PyPI downloads of `specify-cli` in the last month (E-SDD-07). Thoughtworks placed it in Assess in April 2026 and reported several of its teams experimenting with it, "mostly in brownfield environments" (E-SDD-64). No funding applies (GitHub project); no named customers were found.
- **Who launches the agent.** By default the agent drives itself: the README says to run the skills "in your agent's chat, not your terminal, one at a time, reviewing each result before continuing" (E-SDD-02). Since April 2026 there is also a workflow engine in which the `specify` CLI runs YAML-defined steps and dispatches `command`/`prompt` steps to an agent integration "capable of CLI execution", with per-workflow model and reasoning-effort defaults (E-SDD-03, E-SDD-04, E-SDD-05).
- **What verifies.** In the manual flow, `converge` is a prompt asking the agent to "assess the current codebase against the feature's spec, plan, and tasks" and append missing work, i.e. a model's judgment (E-SDD-06, E-SDD-02). In the workflow engine, a `shell` or `command` step "exiting non-zero" halts the run by default, so program-enforced exit codes are available when a workflow author adds shell steps (E-SDD-04). The bundled SDD workflow's gates are human review gates "after specification and planning" (E-SDD-03). Enforcement is therefore opt-in and author-defined, not a built-in mandatory test gate (E-SDD-03, E-SDD-04).
- **Other axes.** Isolation: no worktree or sandbox feature was documented on the pages opened; the docs warn that catalog workflows are not audited (E-SDD-02, E-SDD-03). Planned-vs-touched file reconciliation: not found. Lifecycle/approval: workflow gates take a verdict interactively or through a declared input such as `speckit_review_spec_verdict=approve` (E-SDD-03). Drift: `converge` re-assesses code against spec by model (E-SDD-06). Findings tracking: bug-fix extension reports a verdict `verified`/`partial`/`failed` (E-SDD-02); no finding ids were found. Records: each workflow run persists `state.json` and a step log under `.specify/workflows/runs/<run_id>/` (E-SDD-04). Cost tracking: not found. Multi-agent: integrations for many agents; fan-out with `max_concurrency` in workflows (E-SDD-02, E-SDD-04). JSON: "JSON run, status, and definition interfaces" for workflows (E-SDD-04).
- **Weaknesses and criticism.** Böckeler (Oct 2025, possibly stale): "spec-kit created a LOT of markdown files for me to review" and "I frequently saw the agent ultimately not follow all the instructions" (E-SDD-62). Zaninotto measured "8 files and 1,300 lines of text" for one example (E-SDD-69). Thoughtworks teams reported "instruction bloat" and "overly verbose markdown outputs that increased cognitive load" (E-SDD-64). A user issue reported hitting Claude Pro usage limits "in under an hour of active work" (E-SDD-08). Thoughtworks' Nov 2026 "AI-driven documentation sprawl" Caution blip names "Spec-kit or BMAD" as generators of unmaintained Markdown (E-SDD-66).

The README calls these "Mandatory workflows, not suggestions", but enforcement is by prompt, and the same README admits sessions where "the agent ignores its plan, repeats work, or burns more tokens than you'd expect" (E-SDD-39). The author describes the skills as using persuasion principles (E-SDD-41).
- **Other axes.** Isolation: a skill creates a git worktree after design approval and "verifies clean test baseline" (E-SDD-39). Review: two-stage (spec compliance, then code quality) by subagent (E-SDD-39). Reconciliation, artifact status lifecycle, finding ids, persistent audit records, cost tracking, JSON interface: not found.

### cc-sdd and spec-workflow-mcp

- **cc-sdd.** An MIT-licensed npm installer (`npx cc-sdd@latest`) of 17 Kiro-style Agent Skills for 8 agents; created 2025-07-17, latest `v3.1.0` 2026-09-23, 3,778 stars, 74,039 npm downloads in the last 30 days (E-SDD-42). The host agent drives; `/kiro-impl` runs a per-task implementer, an independent reviewer that "runs `git diff`, greps for TODOs, runs the test suite, and checks task-boundary compliance", and a debugger, when the host has subagents (E-SDD-42). Humans "approve the contract at phase gates" (E-SDD-42). Tasks carry `_Boundary:_` annotations and review looks for boundary violations — the closest documented analogue of planned-vs-touched reconciliation, but performed by a reviewer agent, not a program (E-SDD-42). The README itself warns that installing the skills "does not verify that a host can run the full autonomous loop" and that separate chats "do not by themselves isolate file edits" (E-SDD-42).
- **spec-workflow-mcp.** A GPL-3.0 MCP server with a web dashboard and VS Code extension offering Requirements → Design → Tasks with an "Approval Workflow - Complete approval process with revisions" and "Implementation Logs" (E-SDD-43). 4,303 stars; last npm version 2.2.5 on 2026-03-02; 3,054 downloads in the last 30 days; the maintainer's README says he has "taken a small break from this repo" (E-SDD-43). ## Claims

- **C-SDD-01** — The most-adopted SDD tools are prompt/skill packs in which the coding agent drives itself and the tool's own program verifies only document structure, not the work: Spec Kit's manual flow, OpenSpec, BMAD-METHOD, Superpowers, GSD Core, cc-sdd, Agent OS (E-SDD-02, E-SDD-12, E-SDD-14, E-SDD-27, E-SDD-39, E-SDD-40, E-SDD-38, E-SDD-42, E-SDD-33). Confidence: high.
- **C-SDD-02** — In those packs, "verification" is a model's judgment, a checklist the agent ticks, or a human walk-through, and it is advisory: OpenSpec's verify "does not block archive", Spec Kit's `converge` is a prompt, GSD uses a verifier agent plus human UAT, Superpowers and cc-sdd tell the model to run commands and check exit codes (E-SDD-14, E-SDD-06, E-SDD-38, E-SDD-40, E-SDD-42). Confidence: high.
- **C-SDD-03** — During 2026 several projects added a deterministic runner outside the model that launches agent CLIs step by step: Spec Kit's workflow engine (April 2026), BMad Loop (June 2026), Kiro Workflows, Task Master's `loop`, OpenAI Symphony (February 2026) (E-SDD-05, E-SDD-04, E-SDD-28, E-SDD-20, E-SDD-35, E-SDD-61). Confidence: high.
- **C-SDD-04** — BMad Loop is the closest documented functional overlap with the subject tool: a program-controlled loop, the project's own verify commands run before commit, failures fed back to a fix session, separate fresh-context review optionally on another CLI or model, optional worktree per story, a findings ledger with ids, token budgets, `--json` output and detached runs (E-SDD-28). It is an early beta with 193 stars, tied to BMAD projects, isolation off by default, and run state kept per machine rather than on a Git branch (E-SDD-28). Confidence: high on the features as documented, medium on how they behave in practice (README only).
- **C-SDD-05** — Spec Kit can now express program-enforced gates (a `shell` or `command` step exiting non-zero halts the run) and persists per-run state with JSON status, but its bundled SDD workflow ships human review gates after specification and planning, not test gates; exit-code gates are something a workflow author adds (E-SDD-04, E-SDD-03). Confidence: high.
- **C-SDD-06** — Kiro is the broadest proprietary overlap: runtime-executed workflow graphs with fresh-session reviewers, per-step model and effort, evidence loops, hooks that run shell commands and can deny tool calls, generated property-based tests, headless CLI and cloud sandboxes (E-SDD-18, E-SDD-19, E-SDD-20, E-SDD-21, E-SDD-22). It is closed-source, credit-priced, and its terms prohibit routing through third-party automation harnesses, so it cannot be one of several providers under another runner (E-SDD-15, E-SDD-16). Confidence: high.
- **C-SDD-07** — No tool opened in this session documents a program that compares the files a plan declared with the files a phase actually touched; the nearest are cc-sdd's `_Boundary:_` annotations checked by a reviewer agent, BMad Loop's check "that code actually changed", and GSD plans that list "the files to touch" (E-SDD-42, E-SDD-28, E-SDD-38). Confidence: medium (absence of evidence across READMEs and docs pages, not an exhaustive code audit).
- **C-SDD-08** — No tool opened documents a spec/plan status lifecycle with a staleness state and recorded approvals comparable to Draft → Approved → Completed / Abandoned / Stale; the nearest are spec-workflow-mcp's approval workflow with revisions, Spec Kit's gate verdict inputs, OpenSpec's propose → apply → archive, and cc-sdd's human phase gates (E-SDD-43, E-SDD-03, E-SDD-12, E-SDD-42). Confidence: medium.
- **C-SDD-09** — Spec staleness and drift are recognised as the unsolved weakness of SDD by an independent analyst and by vendors: Thoughtworks says "maintaining the persistent spec still requires discipline" and warns of "unmaintained and contradictory specs"; Augment says a stale spec "misleads agents that don't know any better" and answers with agent-updated "living specs" (E-SDD-65, E-SDD-66, E-SDD-59). Confidence: high.
- **C-SDD-10** — The dominant independent criticism of SDD is review burden from generated Markdown and agents not following it: "I'd rather review code than all these markdown files", "I frequently saw the agent ultimately not follow all the instructions" (Böckeler, Oct 2025); "8 files and 1,300 lines of text", "review time doubles" (Zaninotto, Nov 2025); "overly verbose markdown outputs" (Thoughtworks, Apr 2026); "AI-driven documentation sprawl" in Caution (Thoughtworks, Nov 2026) (E-SDD-62, E-SDD-69, E-SDD-64, E-SDD-66). Confidence: high; the two most-quoted hands-on reviews are older than 12 months.
- **C-SDD-11** — Thoughtworks' November 2026 Radar ties unattended agent work to exactly three prerequisites — "sandboxed execution, work specified up front as in spec-driven development and feedback sensors" — and says teams "need a harness they've tested to validate the changes instead of relying on human code review" (E-SDD-67). Confidence: high.
- **C-SDD-12** — Independent 2026 experiments on martinfowler.com cut both ways for gate-heavy tooling: a behavioural harness with deterministic tests lifted a cost-optimised model from 3/10 to 10/10 accepted runs at a lower cost than the unharnessed frontier model, but added only overhead for the frontier model (Jain, Oct 2026); and instructing an agent to do TDD inside its own loop showed no clear quality gain at roughly 3x–8.5x the tokens in a small informal test (Böckeler, Aug 2026) (E-SDD-71, E-SDD-70). Confidence: medium (single task and small samples; the TDD test concerns tests written by the same agent in the same loop, not separately judged acceptance tests).
- **C-SDD-13** — SDD usage is still growing by registry and star counts but consolidating onto a few tools: OpenSpec npm downloads rose from 32,892 (Nov 2025) to 3,925,435 (Oct 2026); Spec Kit reached 1.0 in August 2026 with 151,322 stars; Superpowers has 326,110 stars; meanwhile Task Master fell from 179,833 to 60,210 monthly downloads with no release since March 2026, the original GSD repository was abandoned for a successor with a fraction of its stars, spec-workflow-mcp's maintainer paused, and Agent OS has had no release since January 2026 (E-SDD-10, E-SDD-01, E-SDD-39, E-SDD-34, E-SDD-36, E-SDD-37, E-SDD-43, E-SDD-33). Confidence: medium (npm downloads and stars are weak proxies for users; download counts include automation).
